# 2단계: 라이브 방송 송출·시청

## Problem Statement

1단계에서는 이미 녹화된 영상만 등록하고 볼 수 있다. 지금 이 순간을 보여 주고 싶은 사람은 휴대폰 하나로 바로 방송을 시작할 방법이 없고, 시청자는 어떤 방송이 지금 진행 중인지, 이미 끝났는지 알 수 없다. 계정을 만들거나 별도 방송 프로그램을 설치하는 절차는 부담이다. 다른 사람이 남의 방송을 끄거나 그 이름으로 송출하는 일도 막아야 한다.

## Solution

1단계 서비스에 **라이브 방송**을 더한다.

- **송출자**는 휴대폰 브라우저로 송출 화면을 열어 제목을 입력하고, 전면·후면 카메라를 골라 미리보기를 확인한 뒤 "방송 시작"을 누른다. 카메라와 마이크 영상이 실시간으로 나가고, "방송 종료"를 누르면 끝난다. 로그인은 없고, 시작할 때 받은 **송출 키**가 송출자임을 증명한다.
- **시청자**는 **방송 목록**의 "라이브 방송" 섹션에서 **방송 중**인 라이브 방송을 골라 다른 화면(PC 브라우저 등)에서 지연 1초 안팎으로 본다. 방송이 끝나면 "방송이 종료되었습니다"가 보인다.
- 라이브 방송의 상태는 **대기 → 방송 중 → 종료**로만 움직이고, 목록에는 방송 중과 종료만 구분해 보인다.
- 1단계의 녹화방송 등록·목록·상세·재생은 그대로 유지된다.

## User Stories

### 송출 준비

1. 송출자로서, 로그인하지 않고 휴대폰 브라우저에서 라이브 방송을 시작하고 싶다. 계정 없이 바로 방송할 수 있도록.
2. 송출자로서, 헤더의 "방송 시작" 링크로 송출 화면에 가고 싶다. 어디서든 바로 방송을 준비할 수 있도록.
3. 송출자로서, 라이브 방송에 제목을 붙이고 싶다. 시청자가 목록에서 알아볼 수 있도록.
4. 송출자로서, 제목이 비었거나 100자를 넘으면 안내를 받고 싶다. 녹화방송과 같은 규칙으로 고칠 수 있도록.
5. 송출자로서, 방송 전에 전면 카메라와 후면 카메라 중 하나를 고르고 싶다. 내 얼굴이나 주변 풍경 중 보여 줄 것을 정할 수 있도록.
6. 송출자로서, 방송 전에 카메라 미리보기를 보고 싶다. 화면이 제대로 나오는지 확인한 뒤 시작할 수 있도록.
7. 송출자로서, 브라우저가 카메라·마이크 권한을 물으면 허용하고 바로 미리보기를 보고 싶다. 권한 단계에서 막히지 않도록.
8. 송출자로서, 카메라·마이크 권한을 거부했거나 기기를 찾지 못하면 이유와 해결 방법을 안내받고 싶다. 브라우저 설정에서 권한을 다시 켤 수 있도록.
9. 송출자로서, 페이지가 HTTPS가 아니어서 카메라를 쓸 수 없으면 그 사실을 안내받고 싶다. 접속 주소를 고칠 수 있도록.

### 송출

10. 송출자로서, "방송 시작"을 누르면 내 카메라와 마이크가 실시간으로 나가고 싶다. 시청자가 지금 모습을 볼 수 있도록.
11. 송출자로서, 영상이 실제로 서버에 도착해 방송 중이 되면 화면에서 "방송 중" 표시를 보고 싶다. 방송이 제대로 나가고 있다고 믿을 수 있도록.
12. 송출자로서, 방송 시작 후 연결이 되지 않으면 안내를 받고 싶다. 네트워크나 방화벽을 확인할 수 있도록.
13. 송출자로서, 방송 중에도 내 화면에서 송출 중인 영상을 보고 싶다. 무엇이 나가고 있는지 확인할 수 있도록.
14. 송출자로서, 방송 중 송출 화면에서 시청 화면으로 가는 링크를 보고 싶다. 다른 기기로 주소를 옮겨 직접 확인할 수 있도록.
15. 송출자로서, "방송 종료"를 누르면 송출이 멈추고 라이브 방송이 종료되기를 원한다. 원할 때 방송을 끝낼 수 있도록.
16. 송출자로서, 방송을 종료하면 카메라와 마이크가 꺼지기를 원한다. 종료 뒤에도 기기가 켜져 있지 않도록.
17. 송출자로서, 실수로 탭을 닫거나 네트워크가 끊기면 라이브 방송이 자동으로 종료되기를 원한다. 목록에 끝난 방송이 방송 중으로 남지 않도록.
18. 송출자로서, 송출 화면을 새로고침해도 같은 브라우저 탭에서는 내 라이브 방송을 종료할 수 있기를 원한다. 실수로 새로고침해도 방송을 끌 수 있도록.
19. 송출자로서, 종료한 뒤 다시 방송하려면 새 라이브 방송을 시작하고 싶다. 지난 방송과 새 방송이 섞이지 않도록.

### 송출 키

20. 송출자로서, 라이브 방송을 시작할 때 나만 아는 송출 키를 받고 싶다. 계정 없이도 내 방송임을 증명할 수 있도록.
21. 송출자로서, 송출 키를 모르는 사람이 내 라이브 방송으로 영상을 보내지 못하기를 원한다. 남이 내 방송을 가로채지 않도록.
22. 송출자로서, 송출 키를 모르는 사람이 내 라이브 방송을 종료하지 못하기를 원한다. 시청자가 장난으로 방송을 끄지 않도록.
23. 송출자로서, 송출 키가 목록이나 시청 화면 응답에 드러나지 않기를 원한다. 누구도 화면이나 응답에서 키를 알아낼 수 없도록.

### 시청

24. 시청자로서, 로그인하지 않고 방송 목록에서 라이브 방송을 보고 싶다. 바로 시청할 수 있도록.
25. 시청자로서, 방송 목록 위쪽 "라이브 방송" 섹션에서 방송 중인 라이브 방송을 먼저 보고 싶다. 지금 볼 수 있는 방송을 바로 찾도록.
26. 시청자로서, 라이브 방송마다 "방송 중" 또는 "종료" 배지를 보고 싶다. 볼 수 있는 방송과 끝난 방송을 구분할 수 있도록.
27. 시청자로서, 방송 중인 라이브 방송은 최근에 시작한 것부터 보고 싶다. 새로 시작한 방송을 먼저 볼 수 있도록.
28. 시청자로서, 종료된 라이브 방송은 최근에 끝난 것 몇 개만 보고 싶다. 목록이 끝난 방송으로 가득 차지 않도록.
29. 시청자로서, 아직 영상이 들어오지 않은(대기) 라이브 방송은 목록에서 보지 않고 싶다. 눌렀는데 아무것도 안 나오는 일이 없도록.
30. 시청자로서, 방송 목록이 몇 초마다 저절로 갱신되기를 원한다. 새로고침하지 않아도 새 방송과 종료를 알 수 있도록.
31. 시청자로서, 방송 중인 라이브 방송을 누르면 시청 화면에서 실시간 영상과 소리를 보고 싶다. 송출자와 거의 같은 시간에 볼 수 있도록.
32. 시청자로서, 시청 화면에서 제목, 상태, 시작 시각을 보고 싶다. 무엇을 언제부터 보고 있는지 알 수 있도록.
33. 시청자로서, 보는 도중 방송이 끝나면 플레이어가 멈추고 "방송이 종료되었습니다"를 보고 싶다. 화면이 멈춘 것인지 끝난 것인지 헷갈리지 않도록.
34. 시청자로서, 종료된 라이브 방송을 누르면 "방송이 종료되었습니다"와 시작·종료 시각을 보고 싶다. 놓친 방송이 언제 있었는지 알 수 있도록.
35. 시청자로서, 아직 대기 중인 라이브 방송의 주소로 들어가면 "곧 방송이 시작됩니다"를 보고, 방송 중이 되면 저절로 재생되기를 원한다. 송출자가 미리 준 링크로 기다릴 수 있도록.
36. 시청자로서, 없는 라이브 방송의 주소로 들어가면 "찾을 수 없음"과 목록 링크를 보고 싶다. 잘못된 링크에서 빠져나올 수 있도록.
37. 시청자로서, 라이브 영상 연결이 실패하면 안내 문구를 보고 싶다. 화면이 멈춘 것처럼 보이지 않도록.
38. 시청자로서, 브라우저 자동재생 정책 때문에 소리가 막히면 소리 켜기 버튼을 보고 싶다. 직접 눌러 소리를 들을 수 있도록.

### 녹화방송 유지

39. 시청자로서, 방송 목록 아래쪽 "녹화방송" 섹션에서 1단계 녹화방송 목록을 그대로 보고 싶다. 라이브가 추가되어도 기존 기능을 그대로 쓸 수 있도록.
40. 등록자로서, 1단계 녹화방송 등록·상세·재생을 그대로 쓰고 싶다. 2단계가 기존 기능을 망가뜨리지 않도록.

### 운영·접속

41. 운영자로서, 서비스를 재시작해도 라이브 방송 기록(제목, 상태, 시작·종료 시각)이 남기를 원한다. 방송 이력이 사라지지 않도록.
42. 운영자로서, 서비스가 재시작되는 동안 방송 중이던 라이브 방송이 종료로 정리되기를 원한다. 재시작 뒤 유령 방송이 남지 않도록.
43. 채점자로서, 명령 하나로 전체 서비스(라이브 포함)를 띄우고 싶다. JDK와 Node 없이 확인할 수 있도록.
44. 채점자로서, 휴대폰을 같은 Wi-Fi에 연결하고 PC의 LAN 주소로 HTTPS 페이지를 열고 싶다. 휴대폰 카메라를 쓸 수 있도록.
45. 채점자로서, 자체 서명 인증서 경고를 넘어가는 방법을 README에서 보고 싶다. 휴대폰 브라우저에서 막히지 않도록.
46. 채점자로서, PC 방화벽에서 열어야 할 포트와 명령을 README에서 보고 싶다. 휴대폰이 PC에 접속할 수 있도록.
47. 채점자로서, PC의 LAN IP를 환경변수 하나로 지정하고 싶다. 내 환경에 맞게 바로 실행할 수 있도록.
48. 채점자로서, README 절차대로 휴대폰으로 송출하고 PC에서 시청한 뒤 종료를 확인하고 싶다. 요구사항 충족을 직접 검증할 수 있도록.
49. 개발자로서, 휴대폰 없이 PC 웹캠과 `localhost`로 송출·시청을 확인하고 싶다. HTTPS와 방화벽 설정 없이 빠르게 개발할 수 있도록.

## Implementation Decisions

### 도메인

- **라이브 방송**은 식별자, 제목, 상태, 송출 키(해시로만 저장), 생성 시각, 시작 시각(방송 중이 된 시각), 종료 시각을 가진다. 등록자(소유자)는 두지 않는다(3단계).
- 제목 규칙은 녹화방송과 같다: 앞뒤 공백 제거 후 1~100자. 녹화방송의 제목 규칙과 메시지를 재사용한다.
- 상태 전환은 이 세 가지뿐이다. 다른 전환은 거부한다.
  - 대기 → 방송 중: 영상이 들어옴
  - 대기 → 종료: 시간 초과, 송출자 종료, 끊김
  - 방송 중 → 종료: 송출자 종료, 끊김
- 대기가 `LIVE_PENDING_TIMEOUT`(기본 60초)을 넘으면 종료로 본다. 조회할 때 판정해서 저장하고, 주기 작업도 같은 규칙으로 정리한다.
- 시간은 주입된 시계로 얻는다(테스트에서 바꿔 끼울 수 있게).
- 서비스가 시작될 때 대기·방송 중으로 남은 라이브 방송은 모두 종료로 정리한다. 재시작하면 MediaMTX의 연결도 끊겨 있기 때문이다.
- **송출 키**: 생성할 때 충분히 긴 무작위 값(URL-safe)을 만들어 응답으로 한 번만 돌려주고, DB에는 SHA-256 해시만 저장한다. 비교는 상수 시간으로 한다.

### 백엔드 모듈

- **라이브 방송 모듈**: 시작(생성), 종료(송출 키 확인), 목록, 단건 조회, 송출 허가 판단, 영상 들어옴·끊김 반영을 제공하는 깊은 모듈. 웹 계층과 MediaMTX 훅 엔드포인트는 이 모듈의 인터페이스만 호출한다.
- **녹화방송 모듈**은 바꾸지 않는다. 공통 오류 처리(Problem Details, 필드별 `errors`, 찾을 수 없음)는 그대로 재사용하고, 권한 없음(403)과 상태 충돌(409)을 공통 처리에 추가한다.

### 공개 API (인증 없음)

- `POST /api/live-broadcasts`: JSON `{ title }`.
  - 성공하면 `201 Created`와 `Location`을 준다. 본문은 `{ id, title, status: "PENDING", streamKey, whipUrl, createdAt }`이고, `streamKey`는 이 응답에서만 나온다.
  - 제목 위반이면 `400`과 Problem Details(`errors`에 `title`)를 준다.
- `POST /api/live-broadcasts/{id}/end`: `Authorization: Bearer <송출 키>` 헤더가 필요하다.
  - 성공하면 `200`과 상세를 준다. 상태는 종료이고 종료 시각이 채워진다.
  - 키가 없거나 틀리면 `403`이다.
  - 이미 종료됐으면 `409`이고, 없는 방송이면 `404`다.
- `GET /api/live-broadcasts`: 방송 목록용이다.
  - 방송 중인 것 전부를 시작 시각 내림차순으로 준다. 그 뒤에 종료된 것 중 최근 10개를 종료 시각 내림차순으로 이어 준다. 대기는 넣지 않는다.
  - 각 항목은 `id`, `title`, `status`, `startedAt`, `endedAt`이다.
- `GET /api/live-broadcasts/{id}`: `id`, `title`, `status`(`PENDING`/`LIVE`/`ENDED`), `createdAt`, `startedAt`, `endedAt`, `whepUrl`. 대기 방송도 조회할 수 있다(링크로 기다리는 시청자용). 송출 키는 절대 포함하지 않는다. 없으면 `404`다.
- `whipUrl`·`whepUrl`은 같은 출처 기준 경로다: `/media/live/{id}/whip`, `/media/live/{id}/whep`.

### MediaMTX 연동 (내부 엔드포인트)

- MediaMTX의 경로 이름은 `live/{id}`이다.
- 인증은 MediaMTX의 HTTP 인증 방식으로 하고, 백엔드의 내부 인증 엔드포인트가 판정한다. 허용이면 `200`, 거부면 `401`이다.
  - `publish`(송출): 그 라이브 방송이 대기이고 시간 초과 전이며, Bearer 토큰으로 온 송출 키가 맞을 때만 허용한다.
  - `read`(시청): 그 라이브 방송이 방송 중일 때만 허용한다.
  - 그 밖의 행동(API, 지표 등)과 `live/{숫자}` 형식이 아닌 경로는 거부한다.
- 상태 훅: MediaMTX의 "영상 준비됨"·"영상 끊김" 훅이 백엔드 내부 엔드포인트를 경로 이름과 함께 호출한다. 백엔드는 대기 → 방송 중, 대기·방송 중 → 종료로 반영한다. 이미 종료된 방송에 들어온 훅은 무시하고 `200`을 준다(멱등).
- 내부 엔드포인트는 `/internal/` 아래에 둔다. Compose 내부 네트워크에서만 닿도록, 앞단 프록시(Caddy, nginx, Vite)는 `/internal/`을 전달하지 않는다. 백엔드 포트도 호스트에 열지 않는다.
- 훅 명령에는 HTTP 클라이언트가 필요하다. 이 클라이언트가 들어 있는 MediaMTX 이미지 변형을 쓴다.

### 스키마

- 새 Flyway 마이그레이션 `V2`로 라이브 방송 테이블을 만든다. 1단계 `V1`은 고치지 않는다.
- 컬럼:
  - 식별자: 자동 증가 bigint
  - 제목: 최대 100자, not null
  - 상태: not null
  - 송출 키 해시: not null
  - 생성 시각: timestamptz, not null
  - 시작 시각: timestamptz, null 허용
  - 종료 시각: timestamptz, null 허용
- 상태별 목록 조회를 위해 상태 인덱스를 둔다.

### 미디어 경로와 프록시

- 브라우저는 항상 같은 출처의 `/media/...`로 WHIP/WHEP을 호출하고, 앞단 프록시가 `/media` 접두어를 떼서 MediaMTX의 WebRTC HTTP 포트로 넘긴다.
  - 전체 실행의 HTTPS 입구: Caddy
  - 전체 실행의 PC용 `localhost:3000`: nginx
  - 개발 실행: Vite 개발 서버
- **Caddy**(새 서비스): `https://{PUBLIC_HOST}:{HTTPS_PORT}`에서 로컬 CA 인증서(내부 발급)로 TLS를 제공한다(ADR-0004). `/media/*`는 MediaMTX로, 나머지는 프론트 nginx로 보낸다. 업로드 한도는 1단계 설정과 같게 유지한다.
- **MediaMTX**(새 서비스): WebRTC만 켠다(RTSP·RTMP·HLS·SRT는 끈다). 미디어 포트는 `WEBRTC_PORT`(기본 8189)이고 UDP·TCP를 모두 쓴다. ICE 후보로 `PUBLIC_HOST`를 알린다(ADR-0003).

### 설정·환경변수 (새로 추가)

- `PUBLIC_HOST`: 휴대폰이 접속할 PC의 LAN IP(예: `192.168.0.5`). Caddy 인증서와 MediaMTX ICE 후보에 쓰인다. 기본값은 `localhost`이고, 이 값으로는 PC에서만 접속할 수 있다.
- `HTTPS_PORT`: Caddy HTTPS 포트(기본 `8443`).
- `WEBRTC_PORT`: MediaMTX 미디어 포트(기본 `8189`, UDP·TCP).
- `LIVE_PENDING_TIMEOUT`: 대기 시간 초과(기본 `60s`).
- `.env.example`과 README에 추가한다. 1단계 환경변수는 그대로다.

### 프론트엔드

- **미디어 어댑터**: 브라우저 미디어 API(`getUserMedia`, `RTCPeerConnection`, WHIP/WHEP HTTP 교환)를 감싸는 얇은 모듈 하나. 화면은 이 모듈만 호출하고, 앱은 실행할 때 이 모듈을 주입받는다(테스트에서는 가짜로 바꾼다). 하는 일:
  - 미리보기 열기: 전면/후면 지정. 권한 거부, 기기 없음, 보안 컨텍스트 아님을 구분한 오류를 낸다.
  - 송출 시작: WHIP URL과 송출 키를 받는다.
  - 송출 중지: 트랙과 연결을 모두 닫는다.
  - 시청 연결: WHEP URL로 원격 스트림을 받는다.
  - 연결 상태 변화와 끊김을 알린다.
- **방송 목록 `/`**: 위에 "라이브 방송" 섹션을 새로 둔다. 항목에는 제목, 방송 중·종료 배지, 시작 또는 종료 시각을 보여 주고 5초마다 다시 불러온다. 라이브 방송이 없으면 안내와 "방송 시작" 링크를 보여 준다. 아래 "녹화방송" 섹션은 1단계 그대로다.
- **송출 화면 `/live/new`**:
  - 제목, 전면/후면 카메라 선택, 미리보기를 둔다.
  - "방송 시작"을 누르면 순서대로: 라이브 방송 생성 → 송출 키를 탭 단위 저장소(sessionStorage)에 보관 → 어댑터로 송출 시작 → 방송 중이 될 때까지 3초마다 상태 확인 → "방송 중" 표시와 시청 화면 링크.
  - "방송 종료"를 누르면 어댑터 송출 중지, 종료 API 호출, 카메라 끄기를 한다.
  - 권한·HTTPS·연결 실패 안내를 보여 준다.
- **시청 화면 `/live/:id`**: 제목, 상태 배지, 시각을 보여 주고 3초마다 상세를 다시 불러온다. 상태별 동작은 다음과 같다.
  - 대기: "곧 방송이 시작됩니다"
  - 방송 중: 어댑터로 시청 연결 후 재생. 자동재생으로 소리가 막히면 "소리 켜기" 버튼
  - 종료: 연결을 닫고 "방송이 종료되었습니다"
  - 연결 실패: 안내 문구
  - 404: "찾을 수 없음"과 목록 링크
- 헤더에 "방송 시작" 링크를 추가한다. 기존 "목록", "녹화방송 등록" 링크는 그대로 둔다.
- 개발 시 Vite가 `/api`와 함께 `/media`도 프록시한다. 대상은 환경변수로 바꿀 수 있다.

### 실행·배포

- 전체 실행: `docker compose up --build`에 `mediamtx`와 `caddy` 서비스를 더한다. 접속 주소는 두 가지다.
  - PC: 기존 `http://localhost:3000`. `localhost`라서 PC 웹캠 송출도 된다.
  - 휴대폰과 다른 기기: `https://{PUBLIC_HOST}:{HTTPS_PORT}`
- 개발 실행: DB와 MediaMTX는 compose로 띄우고(`docker compose up -d db mediamtx`) 백엔드는 `bootRun`, 프론트는 `npm run dev`로 실행한다. 이때 MediaMTX 훅과 인증은 호스트에서 도는 백엔드를 호출해야 하므로, 대상 주소를 환경변수로 바꿀 수 있게 한다(기본은 compose 내부 백엔드).
- 휴대폰 확인은 전체 실행에서만 한다.
- 방화벽은 사용자가 직접 연다. `HTTPS_PORT`/TCP와 `WEBRTC_PORT`/UDP·TCP의 인바운드 허용 명령을 README에 적는다.

## Testing Decisions

- 좋은 테스트는 외부에서 관찰할 수 있는 동작만 검증한다. 내부 클래스 구조, 호출 순서, 리포지토리 호출 여부는 검증하지 않는다. 동작이 같으면 구조를 바꿔도 테스트는 그대로 green이어야 한다.
- 모든 기능과 버그 수정은 red → green으로 진행하고, 사이클마다 `docs/tdd-log.md`에 기록한다. 병행 작업 중에는 1단계처럼 티켓 파일의 `## TDD 기록`에 남기고 병합 때 옮긴다.
- **경계 1: 백엔드 HTTP API** (1단계와 같다). 앱 전체를 띄우고 Testcontainers의 실제 PostgreSQL을 쓰며, REST API 호출과 응답으로만 검증한다. MediaMTX는 띄우지 않고, MediaMTX가 보낼 인증·상태 훅 요청을 테스트가 내부 엔드포인트로 직접 보낸다. 시간은 주입된 시계만 테스트 설정에서 바꿔 끼운다. 다루는 범위:
  - 시작: `201`, 송출 키는 응답에서만 나옴, 목록에는 대기가 보이지 않음, 제목 위반 `400`
  - 송출 인증 허용: 맞는 키 + 대기
  - 송출 인증 거부: 틀린 키, 키 없음, 종료됨, 시간 초과, 이상한 경로·행동
  - 시청 인증: 방송 중만 허용
  - 상태 훅: 영상 들어옴 → 방송 중(시작 시각), 끊김 → 종료(종료 시각), 종료 후 훅은 멱등
  - 종료 API: 성공 `200`, 키 없음·틀림 `403`, 이미 종료 `409`, 없음 `404`
  - 대기 시간 초과 → 조회 시 종료
  - 목록: 방송 중 시작 시각 내림차순 → 종료 최근 10개 종료 시각 내림차순
  - 상세와 목록 응답 어디에도 송출 키·해시가 없음
  - 재시작 정리: 시작 시점에 남은 대기·방송 중을 종료로 정리. 시작 정리 로직을 앱 시작 이벤트로 검증할 수 없다면 이 항목은 직접 확인 절차로 넘긴다.
  - 1단계 녹화방송 API 테스트는 모두 그대로 green이어야 한다.
- **경계 2: 프론트 앱 화면 단위** (1단계 경계 + 미디어 어댑터). 라우터를 포함한 앱 전체를 렌더링하고 전역 `fetch`를 스텁한다. 여기에 미디어 어댑터 하나만 가짜로 주입한다. 가짜는 미리보기·송출·시청의 성공과 실패, 끊김을 흉내 낸다. 화면에 보이는 텍스트와 사용자 동작으로만 검증한다. 다루는 범위:
  - 송출 화면: 제목 검증, 카메라 선택 전달, 권한 거부·HTTPS 아님 안내, 시작 시 생성 API와 어댑터 송출 호출, 방송 중 표시, 종료 시 송출 키를 담은 종료 API 호출과 어댑터 중지, 새로고침 후에도 탭 저장소의 키로 종료
  - 시청 화면: 대기 안내, 방송 중이면 시청 연결, 종료로 바뀌면 안내와 연결 해제, 연결 실패 안내, 404
  - 방송 목록: 라이브 섹션의 배지와 순서, 빈 상태 안내, 녹화방송 섹션 유지
  - 1단계 프론트 테스트는 모두 그대로 green이어야 한다. 헤더 링크 추가로 기존 테스트 질의가 깨지지 않게 이름을 겹치지 않게 짓는다.
- **두 경계로 확인할 수 없는 것**은 README의 직접 확인 절차로 검증한다: 실제 카메라·마이크, WebRTC 미디어 흐름과 지연, 휴대폰 HTTPS·인증서 경고, 방화벽, MediaMTX 훅이 실제로 백엔드를 호출하는지.
- 테스트 실행에는 Docker가 필요하다(Testcontainers). 1단계와 같다.
- 참고할 기존 테스트: 백엔드는 녹화방송 API 경계 테스트들, 프론트는 앱 단위 테스트와 `fetch` 스텁·앱 렌더 도우미다.

## Out of Scope

- 라이브 방송을 녹화방송으로 저장(다시보기)
- 시청자 수, 채팅(3단계 댓글과 별개), 좋아요
- 방송 중 음소거·카메라 전환·화면 필터·화질 조절. 카메라는 시작 전에만 고른다
- TURN 서버와 같은 네트워크 밖(LTE 등)에서의 송출·시청
- 공인 인증서(경고 없는 HTTPS), 도메인
- 로그인, 송출자 프로필, 권한(3단계), 도네이션(4단계)
- 녹화방송 쪽 변경(1단계 기능은 그대로 둔다)
- 라이브 방송 수정·삭제·검색·페이지네이션
- E2E 자동화 테스트

## Further Notes

- 용어는 `GLOSSARY.md`를 따른다: 방송 목록, 라이브 방송, 송출자, 시청자, 송출 키, 대기, 방송 중, 종료. 코드 식별자는 영어 대응어(LiveBroadcast, Broadcaster, Viewer, StreamKey, PENDING/LIVE/ENDED)를 쓴다.
- 관련 결정: ADR-0003(WebRTC WHIP/WHEP + MediaMTX), ADR-0004(Caddy 로컬 CA HTTPS). 1단계 ADR-0001·0002는 그대로다.
- 확인 기기는 Android Chrome(송출)과 PC Chrome(시청)이다. README에는 iOS Safari에서 인증서 경고를 넘기는 방법과 카메라 권한 설정도 적는다.
- README의 직접 확인 절차 순서:
  1. 준비: PC LAN IP 확인 → `PUBLIC_HOST` 설정 → 방화벽 허용 → 전체 실행
  2. 휴대폰을 같은 Wi-Fi에 연결하고 `https://{PUBLIC_HOST}:{HTTPS_PORT}` 접속 → 인증서 경고 넘기기
  3. 송출 화면에서 카메라 선택 → 권한 허용 → 미리보기 → 방송 시작 → "방송 중" 확인
  4. PC 방송 목록에 "방송 중" 배지 확인 → 시청 화면에서 영상·소리 확인
  5. 휴대폰에서 방송 종료 → PC 시청 화면 "방송이 종료되었습니다"와 목록 "종료" 배지 확인
  6. 탭 닫기로 끊김 → 자동 종료 확인
  7. 재시작 후 기록 유지 확인
  8. 1단계 녹화방송 절차가 그대로 되는지 확인
- 2단계를 마치면 `docs/presentation-notes.md`의 2단계 섹션(결정, 결과·수치, 어려웠던 점)을 채우고, 사용자에게 커밋과 `stage-2` 태그를 할지 묻는다.
- PC의 Windows 네트워크 프로필이 "공용"이라 방화벽 허용 없이는 휴대폰이 접속할 수 없다. 방화벽 변경은 사용자가 직접 한다.
