# 4단계: 방송자 후원(도네이션)

## Problem Statement

시청자는 방송을 보며 댓글을 남길 수는 있지만, 마음에 드는 방송자에게 금전적으로 응원할 방법이 없다. 후원을 받으려면 결제가 필요한데, 화면에 "결제 성공"이 떴다는 것만 믿고 적립하면 주소창의 금액을 바꾸거나 성공 화면을 흉내 내는 것만으로 가짜 후원이 쌓일 수 있다. 결제 결과는 화면 새로고침이나 결제 서비스의 재전송으로 여러 번 도착할 수 있어서, 같은 결제가 두 번 적립될 위험도 있다. 방송자와 시청자는 그 방송에 누가 얼마를 후원했는지, 모두 합쳐 얼마인지 볼 수 없다.

## Solution

3단계 서비스에 **후원**을 더한다(ADR-0007, ADR-0008).

- 로그인한 회원이 녹화방송 상세나 라이브 방송 시청 화면에서 **후원하기**를 눌러 그 방송의 방송자(소유자)에게 보낼 금액을 고른다.
- 서버가 주문번호·금액·방송자를 정해 **결제 대기** 후원을 만들고, 토스페이먼츠 결제창(카드, 테스트 모드)으로 결제한다. 실제 돈은 움직이지 않는다.
- 결제 후 돌아오면 서버가 주문·금액·방송자를 확인하고 토스 승인 API로 승인을 받은 뒤 응답을 다시 확인해야만 후원을 **확정**한다. 실패·취소는 적립하지 않는다.
- 같은 결제의 승인 통지(화면의 확인 요청, 토스 웹훅)가 몇 번 와도 후원은 한 번만 확정된다.
- 방송마다 확정된 후원 내역(후원자 닉네임, 금액, 시각)과 합계를 누구나 본다.
- 1~3단계 기능은 그대로 동작한다. 후원 확인에는 인터넷 연결이 필요하고, 나머지 기능은 인터넷 없이도 동작한다.

## User Stories

### 후원하기

1. 시청자로서, 녹화방송 상세와 라이브 방송 시청 화면에서 "후원하기"를 보고 싶다. 그래야 보고 있는 방송의 방송자에게 바로 후원할 수 있다.
2. 후원자로서, 1,000 / 5,000 / 10,000 / 50,000원 빠른 선택 버튼으로 금액을 고르고 싶다.
3. 후원자로서, 원하는 금액을 직접 입력하고 싶다.
4. 후원자로서, 1,000원보다 작거나 1,000,000원보다 크거나 정수가 아닌 금액이면 결제창을 열기 전에 이유를 보고 싶다.
5. 후원자로서, 화면을 거치지 않고 규칙에 어긋나는 금액을 보내도 서버가 거절했으면 한다.
6. 후원자로서, 누구에게 얼마를 후원하는지(방송자 닉네임, 금액) 확인한 뒤 결제창을 열고 싶다.
7. 후원자로서, 결제창에서 테스트 카드로 결제하고 싶다. 실제 돈이 나가지 않아야 한다.
8. 방문자로서, 로그인하지 않았으면 "후원하기" 대신 로그인 안내와 링크를 보고, 로그인하면 그 방송 화면으로 돌아오고 싶다.
9. 서비스 운영자로서, 로그인하지 않은 요청으로 후원을 시작하면(API 직접 호출 포함) 서버가 401로 거절했으면 한다.
10. 방송자로서, 내 방송에는 "후원하기"가 보이지 않았으면 한다. API로 자기 방송에 후원하려 해도 서버가 거절해야 한다.
11. 서비스 운영자로서, 소유자가 없는 옛 방송에는 후원할 수 없었으면 한다(버튼 없음, 서버 거절).
12. 시청자로서, 종료된 라이브 방송에도 후원하고 싶다.
13. 시청자로서, 없는 방송에 후원하려 하면 "찾을 수 없음"을 보고 싶다.

### 승인 확인과 확정

14. 후원자로서, 결제를 마치고 돌아오면 서버가 확인한 결과("후원이 확정되었습니다", 방송자·금액)를 보고 싶다.
15. 후원자로서, 확정 결과 화면에서 후원한 방송으로 돌아가고 싶다.
16. 서비스 운영자로서, 화면에 성공이 표시되었다는 것만으로는 후원이 확정되지 않았으면 한다. 서버가 결제 승인을 직접 확인해야 한다.
17. 서비스 운영자로서, 돌아온 주소의 금액이 후원을 시작할 때 정한 금액과 다르면 승인을 요청하지 않고 거절했으면 한다.
18. 서비스 운영자로서, 다른 회원의 결제 대기 후원을 대신 확정하려 하면 거절했으면 한다.
19. 서비스 운영자로서, 후원을 시작한 뒤 방송 소유자가 바뀌었거나 방송이 사라졌다면 확정하지 않았으면 한다.
20. 서비스 운영자로서, 결제 서비스의 승인 응답이 완료가 아니거나 금액·주문번호가 다르면 확정하지 않았으면 한다.
21. 후원자로서, 결제 서비스와 연결이 잠깐 끊겨 확인하지 못했으면 후원이 사라지지 않고 다시 확인할 수 있었으면 한다.

### 실패·취소

22. 후원자로서, 결제창에서 결제를 그만두면 "후원을 취소했습니다"를 보고 싶다. 적립되면 안 된다.
23. 후원자로서, 결제가 거절되면 이유와 함께 "후원에 실패했습니다"를 보고 싶다. 적립되면 안 된다.
24. 후원자로서, 실패·취소 결과 화면에서 다시 후원하거나 방송으로 돌아가고 싶다.
25. 서비스 운영자로서, 실패·취소된 후원은 나중에 승인 통지가 와도 확정하지 않았으면 한다.

### 중복 통지

26. 후원자로서, 확정 결과 화면을 새로고침해도 후원이 두 번 쌓이지 않았으면 한다.
27. 서비스 운영자로서, 같은 확인 요청이 동시에 두 번 와도 후원이 한 번만 확정되었으면 한다.
28. 서비스 운영자로서, 결제 서비스가 같은 승인 웹훅을 여러 번 보내도 한 번만 적립되었으면 한다.
29. 서비스 운영자로서, 웹훅 본문을 그대로 믿지 않고 결제 서비스에 실제 상태를 다시 물어 확인했으면 한다. 그래야 위조된 웹훅으로 적립되지 않는다.
30. 후원자로서, 결제 직후 창을 닫아 확인 요청을 못 보냈어도, 승인 통지(웹훅)가 오면 후원이 확정되었으면 한다.
31. 서비스 운영자로서, 이미 확정된 후원에 대해 결제 서비스의 승인 API를 다시 부르지 않았으면 한다.
32. 개발자로서, 받은 모든 승인 통지가 언제, 어디서 왔고, 어떻게 처리되었는지(새로 확정·이미 확정·무시·거절) 기록으로 남았으면 한다. 그래야 중복 통지가 무시된 것을 보여 줄 수 있다.

### 후원 내역과 합계

33. 시청자로서, 방송 화면에서 그 방송의 확정된 후원 내역(후원자 닉네임, 금액, 확정 시각)을 최신순으로 보고 싶다.
34. 시청자로서, 그 방송의 후원 합계와 건수를 보고 싶다.
35. 방문자로서, 로그인하지 않아도 후원 내역과 합계를 볼 수 있었으면 한다.
36. 시청자로서, 라이브 방송을 보는 동안 다른 사람의 후원이 몇 초 안에 내역과 합계에 나타났으면 한다.
37. 서비스 운영자로서, 결제 대기·실패·취소 후원은 내역과 합계에 들어가지 않았으면 한다.
38. 방송자로서, 내 방송의 후원 내역과 합계를 다른 시청자와 똑같이 보고 싶다.
39. 서비스 운영자로서, 후원이 있는 방송을 소유자가 삭제해도 후원 기록은 DB에 남았으면 한다(돈이 오간 기록).

### 실행과 확인

40. 채점자로서, 결제 서비스에 가입하지 않고 공개 테스트 키만으로 `docker compose up --build` 후 바로 후원을 해 볼 수 있었으면 한다.
41. 채점자로서, README에서 테스트 결제 성공·실패·취소와 승인 통지 중복을 확인하는 방법을 보고 싶다.
42. 채점자로서, 1~3단계 직접 확인 절차가 그대로 통과하기를 바란다.
43. 개발자로서, 3단계 데이터가 있는 DB에 새 마이그레이션만 적용해 4단계로 올릴 수 있었으면 한다.

## Implementation Decisions

> **변경(2026-11-10, 01 진행 중 사용자 결정)**: 결제창(`payment()`, API 개별 연동 키) 대신 **결제위젯**(`widgets()`, 문서용 공개 키 `test_gck_docs_…`/`test_gsk_docs_…`)을 쓴다. 공식 샘플의 공개 결제창 키가 토스 샌드박스에서 401로 거절되기 때문이다(ADR-0007). 이 문서의 "결제창"은 위젯의 "결제하기"로 이어지는 카드사 테스트 결제 화면을 뜻하고, 후원 시작은 "서버가 주문을 만든다 → 그 금액으로 위젯을 그린다 → 결제하기" 순서다. 위젯은 카드 외 결제수단(간편결제·계좌이체)도 테스트로 보여 주지만 확인은 카드로 한다.


### 모듈

- **후원 모듈(새로)**: 후원 엔티티와 상태, 후원 시작·확인·실패 보고·내역 API, 확정 규칙(멱등), 통지 기록.
- **결제 게이트웨이(새 경계)**: 결제 서비스에 대한 두 동작만 가진 인터페이스. "결제 키·주문번호·금액으로 승인 요청"과 "결제 키로 결제 조회". 결과는 상태(완료/그 밖), 주문번호, 승인 금액, 오류 코드로 돌려준다. 실제 구현은 토스 REST(시크릿 키 Basic 인증)를 Spring `RestClient`로 부르고, 테스트는 가짜 구현으로 바꿔 끼운다.
- **결제 설정**: 클라이언트 키·시크릿 키·API 주소를 환경변수로 받는다. 클라이언트 키는 설정 API로 프론트에 내려 준다(빌드에 넣지 않음).
- **보안 설정(변경)**: 웹훅 경로는 로그인·CSRF 없이 열어 둔다(본문 대신 조회 API를 믿으므로, ADR-0008). 나머지 후원 API는 3단계 규칙(`LoginMember` 401, CSRF)을 따른다.
- **방송 모듈**: 방송 존재와 현재 소유자를 읽기만 한다(고치지 않음). 방송 삭제 이벤트는 후원 모듈이 받지 않는다(기록 유지).
- **프론트 결제창 어댑터(새 경계)**: "주문번호·금액·주문명·성공/실패 주소로 카드 결제창 열기" 한 동작. 실제 구현은 토스 SDK(npm, 버전 고정), 테스트는 가짜(호출만 기록). 2단계 미디어 어댑터처럼 앱에 주입한다.
- **프론트 후원 영역(새로)**: 녹화방송 상세·라이브 시청 화면 아래의 컴포넌트 하나(금액 선택·후원하기·내역·합계). 화면 파일에는 한두 줄로 붙인다. 결과 화면 두 개(성공·실패 복귀).

### 후원 상태

- 결제 대기 → 확정 / 실패 / 취소. 확정 뒤 바뀌지 않는다.
- 내부 상태 하나를 더 둔다: **확인 필요**. 결제 서비스 승인은 끝났는데 응답의 금액·주문번호가 맞지 않는 이상 상황. 적립하지 않고 기록만 남긴다(환불은 범위 밖).
- 결제 대기 주문을 정리하는 작업은 없다. 내역·합계에는 확정만 센다.

### 금액·대상 규칙

- 금액: 원 단위 정수, 1,000 이상 1,000,000 이하. 위반은 400(`errors`에 `amount`).
- 방송자: 후원을 시작하는 순간의 방송 소유자. 소유자가 없는 방송, 자기 방송은 409("후원할 수 없는 방송입니다" 류의 이유). 방송 없음 404.
- 주문명: "<방송 제목> 후원"(결제창 표시용, 길이 제한에 맞게 자른다).

### 확정 규칙 (확인 요청과 웹훅 공통)

1. 주문번호로 후원을 찾고 행을 잠근다(`SELECT … FOR UPDATE`). 없으면 404.
2. 확인 요청이면 후원자가 요청한 회원인지 확인(아니면 403). 웹훅은 이 단계 없음.
3. 이미 확정이고 같은 결제 키면 → **이미 확정**: 결제 서비스를 부르지 않고 기존 결과를 200으로 돌려준다.
4. 실패·취소·확인 필요면 → **거절**(409).
5. 결제 대기면: 요청 금액이 저장 금액과 다르면 → 실패로 바꾸고 **거절**(400). 방송이 없거나 현재 소유자가 저장된 방송자와 다르면 → 실패로 바꾸고 **거절**(409).
6. 확인 요청이면 게이트웨이에 승인 요청. 결제 서비스가 "이미 처리된 결제"라고 하면 조회로 실제 상태를 확인한다. 웹훅이면 처음부터 조회한다.
7. 결과가 완료이고 승인 금액·주문번호가 저장값과 같으면 → **새로 확정**(결제 키·확정 시각 저장). 완료이지만 값이 다르면 → 확인 필요. 결제 서비스가 거절하면 → 실패(오류 코드·메시지 저장). 결제 서비스와 통신 실패면 → 결제 대기로 두고 502(다시 시도 가능).
8. 모든 통지는 통지 기록에 남긴다(결제 키, 주문번호, 출처, 받은 시각, 처리 결과, 짧은 설명).

### 스키마 (Flyway `V4`, 기존 데이터 유지)

- `donation`: `id`, `order_id`(UUID, 유니크), `broadcast_type`, `broadcast_id`, `donor_id`(회원), `streamer_id`(회원), `amount`(정수), `status`, `payment_key`(nullable, 유니크), `failure_code`, `failure_message`, `created_at`, `confirmed_at`. (`broadcast_type`, `broadcast_id`, `status`) 인덱스. 방송에 외래 키는 걸지 않는다(방송 삭제 후에도 기록 유지).
- `payment_notification`: `id`, `payment_key`, `order_id`, `source`(`CONFIRM_REQUEST`/`WEBHOOK`), `result`(`NEW_CONFIRMED`/`ALREADY_CONFIRMED`/`IGNORED`/`REJECTED`), `detail`, `received_at`.

### API 계약

| 메서드 | 경로 | 인증 | 설명 |
| --- | --- | --- | --- |
| `GET` | `/api/payments/config` | 공개 | `{ clientKey }` |
| `POST` | `/api/recordings/{id}/donations`, `/api/live-broadcasts/{id}/donations` | 로그인 | JSON `{ amount }`. `201 { orderId, amount, orderName, streamer: { id, nickname }, customerKey }`. 금액 400, 방송 없음 404, 소유자 없음·자기 방송 409 |
| `POST` | `/api/donations/confirm` | 로그인 | JSON `{ paymentKey, orderId, amount }`. `200 { id, status, amount, streamer, broadcast: { type, id }, confirmedAt }`. 위 확정 규칙의 400/403/404/409/502 |
| `POST` | `/api/donations/fail` | 로그인 | JSON `{ orderId, code, message }`. 결제 대기인 자기 주문을 사용자 취소 코드면 취소, 그 밖은 실패로 바꾼다. `200 { status, broadcast }`. 이미 확정이면 바꾸지 않고 409 |
| `GET` | `/api/recordings/{id}/donations`, `/api/live-broadcasts/{id}/donations` | 공개 | `{ totalAmount, count, items: [{ id, donor: { id, nickname }, amount, confirmedAt }] }`, 확정만, 최신순. 방송 없음 404 |
| `POST` | `/api/payments/toss/webhook` | 공개(CSRF 제외) | 토스 결제 상태 변경 본문(`eventType`, `data.paymentKey`, `data.orderId`, `data.status`). 본문은 결제 키·주문번호를 얻는 데만 쓰고 조회로 확인한다. 200(처리 결과는 통지 기록에). 단, 결제 서비스 조회가 통신 실패하면 502로 답해 재전송을 받는다(04 진행 중 사용자 결정, 2026-11-11) |

- `customerKey`: 후원자를 결제 서비스에 식별시키는 값(회원 식별자에서 만든 무작위가 아닌 고정 문자열, 결제 SDK 규칙에 맞게).
- 성공·실패 주소: 프론트가 `window.location.origin` 기준으로 `/donations/success`, `/donations/fail`을 넘긴다. PC(`http://localhost:3000`)와 휴대폰(`https://<PUBLIC_HOST>:8443`) 모두 같은 방식으로 동작한다.

### 화면

- **후원 영역**(녹화방송 상세·라이브 시청 화면 아래): 합계와 건수, 확정된 후원 내역(최신순). 후원 가능한 회원에게는 금액 빠른 선택(1,000·5,000·10,000·50,000), 직접 입력, "<방송자 닉네임>님에게 <금액>원 후원하기" 버튼. 비로그인은 로그인 안내(`next`로 돌아옴), 소유자 자신과 소유자 없는 방송은 버튼 없음. 라이브 방송은 3초마다 다시 불러온다.
- **후원하기**: 서버에 후원 시작 → 받은 주문번호·금액으로 결제창 어댑터 호출(결제창으로 이동).
- **`/donations/success`**: 주소의 `paymentKey`·`orderId`·`amount`로 확인 요청 → 확정이면 "후원이 확정되었습니다"와 방송자·금액, 방송으로 돌아가는 링크. 확인 중에는 "확인 중…". 서버가 거절하면 이유. 같은 화면을 새로고침해도 같은 결과(중복 적립 없음).
- **`/donations/fail`**: 주소의 `code`·`message`·`orderId`로 실패 보고 → 취소면 "후원을 취소했습니다", 그 밖은 "후원에 실패했습니다"와 이유. 방송으로 돌아가는 링크.
- 서버 거절 안내는 3단계 방식(401 로그인 안내, 403 권한 없음, 그 밖 서버 이유)을 따른다.

### 실행·환경변수

- `TOSS_CLIENT_KEY`, `TOSS_SECRET_KEY`: 기본값은 토스 문서의 공개 테스트 키(구현 시 문서에서 확인해 적는다). `TOSS_API_BASE_URL`: 기본 `https://api.tosspayments.com`.
- compose는 백엔드에 세 값을 넘긴다. 프론트 이미지는 다시 빌드할 필요가 없다.
- 결제창(SDK)과 승인 API는 인터넷의 토스 서버를 쓴다. README에 조건으로 적는다.

## Testing Decisions

- 좋은 테스트는 외부 동작만 본다. 백엔드는 HTTP 요청·응답과 그 뒤의 조회 결과(내역·합계·DB의 후원·통지 기록), 프론트는 사용자가 보는 화면과 나간 요청·어댑터 호출만 확인한다.
- **백엔드: HTTP API 경계** (prior art: `CommentApiTest`, `CommentAuthorApiTest`, `LiveBroadcastControlApiTest`, `MediaMtxHookApiTest`, `MemberTestSupport`의 `signUp`).
  - 결제 게이트웨이를 테스트 설정에서 가짜로 바꾼다(prior art: `MutableClockConfiguration`). 가짜는 승인 성공·거절·이미 처리됨·통신 실패, 조회 결과를 테스트마다 정할 수 있고 호출 횟수를 기록한다.
  - 후원 시작: 비로그인 401, 금액 경계(999·1,000·1,000,000·1,000,001), 방송 없음 404, 소유자 없음·자기 방송 409, 녹화방송·라이브 방송(종료 포함) 모두.
  - 확인: 성공 확정과 내역·합계 반영, 금액 위조 400(승인 API 호출 0회), 다른 회원 403, 실패·취소된 주문 409, 결제 서비스 거절 → 실패, 승인 후 값 불일치 → 확인 필요, 통신 실패 502 후 재시도로 확정, "이미 처리됨" → 조회로 확정.
  - 중복: 같은 확인 요청 두 번 → 합계 한 번, 승인 API 호출 1회, 통지 기록 2줄(새로 확정·이미 확정). 동시 두 요청(스레드 두 개) → 한 건만 확정. 웹훅 두 번 → 한 번 적립. 위조 웹훅(조회 결과가 완료 아님·없는 결제 키) → 무시. 결제 대기 주문에 완료인데 주문번호·금액이 다른 웹훅 → 확인 요청과 같이 확인 필요. 조회 통신 실패 → 502. 확인 요청 후 웹훅 → 이미 확정.
  - 실패 보고: 취소 코드 → 취소, 그 밖 → 실패, 확정된 주문은 바뀌지 않음(409), 다른 회원 403.
  - 내역: 공개, 확정만, 최신순, 합계·건수.
  - 실제 토스 구현(게이트웨이)은 자동 테스트하지 않는다. 요청 모양(인증 헤더·본문)만 필요하면 로컬 가짜 HTTP 서버로 확인한다.
- **프론트: 앱 화면 단위** (prior art: `Comments.test.tsx`, `LiveBroadcastControl.test.tsx`, `renderApp`, `createFakeMediaAdapter`, `stubFetch`).
  - 결제창 어댑터를 가짜로 주입한다. 후원하기 → 후원 시작 요청(CSRF 헤더) → 어댑터가 서버가 준 주문번호·금액으로 호출됨.
  - 금액 검증(빠른 선택, 직접 입력, 범위 밖), 비로그인·소유자·소유자 없음에 따른 버튼 표시, 내역·합계 표시, 라이브 3초 폴링.
  - `/donations/success?...`를 바로 렌더링해 확인 요청 본문과 확정·거절 화면, `/donations/fail?...`로 취소·실패 화면.
- E2E 자동화는 하지 않는다. README 직접 확인 절차: 테스트 카드 결제 성공, 결제창에서 실패 만들기, 결제창 닫기(취소), 확인 요청·웹훅을 `curl`로 반복해 합계가 한 번만 늘고 통지 기록에 "이미 확정"이 남는지 DB로 확인.

## Out of Scope

- 후원 메시지, 익명 후원, 후원 알림(방송 화면 위 효과)
- 환불·결제 취소(확정된 후원 되돌리기), 확인 필요 상태의 자동 처리
- 방송자 정산, 받은 후원 모아 보기, 후원 순위
- 가상계좌 입금 처리(위젯에 보이는 카드 외 결제수단은 테스트로만 열어 두고 확인은 카드로 한다)
- 결제 대기 주문의 만료·정리 작업
- 실제(운영) 결제 키, 결제 서비스 가맹 심사
- 웹훅을 로컬로 받기 위한 터널(공개 주소)
- 후원 내역 페이지네이션
- E2E 자동화 테스트

## Further Notes

- 결정 근거: ADR-0007(토스 테스트 모드 + 서버 승인 확인), ADR-0008(중복 확정 방지). 3단계 ADR-0005(세션·CSRF)를 그대로 따른다.
- 토스 결제창은 다른 주소로 이동했다가 돌아오므로, 확인 요청은 돌아온 화면이 보낸다. 이때 로그인 세션 쿠키가 같은 출처라 그대로 실린다.
- 테스트 카드 번호·실패 재현 방법·사용자 취소 오류 코드·공개 테스트 키는 구현할 때 토스 문서에서 확인하고 README에 출처와 함께 적는다.
- 방송 삭제 시 댓글은 지워지지만(3단계) 후원 기록은 남는다. 삭제된 방송의 후원은 화면에서 볼 곳이 없다.
