# 04: 중복 승인 통지 방지와 웹훅

**What to build:** 같은 결제의 승인 통지가 몇 번, 어떤 경로로 와도 후원은 한 번만 확정된다. 확정 결과 화면을 새로고침하거나 확인 요청을 다시 보내면 결제 서비스를 다시 부르지 않고 같은 결과를 돌려준다. 동시에 온 두 요청도 한 건만 확정된다. 토스 웹훅을 받는 엔드포인트가 있고, 본문 대신 조회 API로 실제 상태를 확인해 같은 규칙으로 처리하며 위조된 통지는 무시한다. 모든 통지가 통지 기록에 처리 결과와 함께 남는다. 스펙: `.scratch/donations/spec.md`, 결정: ADR-0008.

03이 다듬은 확정 규칙 위에서 진행한다. 02가 아직 진행 중이면 병행한다.

> **변경(2026-11-10, 01 진행 중 사용자 결정)**: 결제창(`payment()`, API 개별 연동 키) 대신 **결제위젯**(`widgets()`, 문서용 공개 키 `test_gck_docs_…`/`test_gsk_docs_…`)을 쓴다. 공식 샘플의 공개 결제창 키가 토스 샌드박스에서 401로 거절되기 때문이다(ADR-0007). 이 문서의 "결제창"은 위젯의 "결제하기"로 이어지는 카드사 테스트 결제 화면을 뜻하고, 후원 시작은 "서버가 주문을 만든다 → 그 금액으로 위젯을 그린다 → 결제하기" 순서다. 위젯은 카드 외 결제수단(간편결제·계좌이체)도 테스트로 보여 주지만 확인은 카드로 한다.

**Blocked by:** 03

**Status:** ready-for-agent

- [ ] 확정된 주문에 같은 확인 요청을 다시 보내면 `200` 같은 결과, 합계·건수 그대로, 게이트웨이 승인 호출 총 1회, 통지 기록에 "새로 확정"과 "이미 확정"
- [ ] 같은 확인 요청을 동시에 두 개(스레드 두 개) 보내면 한 건만 확정되고 합계가 한 번만 늘어난다(주문 행 잠금)
- [ ] 결제 키 유니크 제약으로 같은 결제 키가 두 후원에 붙지 않는다
- [ ] 게이트웨이가 "이미 처리된 결제"를 주면 조회로 실제 상태를 확인해 완료·값 일치면 확정한다(승인 뒤 서버가 확정 전에 끊긴 상황)
- [ ] `POST /api/payments/toss/webhook`: 로그인·CSRF 없이 받는다. 본문에서 결제 키만 얻어 조회하고, 완료·주문번호·금액이 맞으면 확정(이미 확정이면 "이미 확정"). 항상 `200`
- [ ] 같은 웹훅 두 번 → 한 번만 적립, 통지 기록 두 줄
- [ ] 확인 요청 뒤 웹훅, 웹훅 뒤 확인 요청 → 어느 쪽이든 한 번만 적립
- [ ] 위조 웹훅(조회 결과가 완료가 아님, 주문번호·금액이 다름, 없는 결제 키) → 적립 안 함, 통지 기록 "무시"
- [ ] 실패·취소된 주문에 온 웹훅 → 확정하지 않음
- [ ] 백엔드 HTTP API 경계 테스트(가짜 게이트웨이, 동시성 테스트 포함)로 위를 확인한다
- [ ] 프론트: `/donations/success` 새로고침·다시 렌더링해도 같은 확정 화면(앱 단위 테스트)
- [ ] README용 확인 방법 초안을 Comments에 적는다: 확인 요청과 웹훅을 `curl`로 반복하는 명령, 통지 기록을 DB에서 조회하는 명령
