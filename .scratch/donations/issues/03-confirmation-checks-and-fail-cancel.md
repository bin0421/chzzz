# 03: 승인 확인 검증과 실패·취소

**What to build:** 결제 후 돌아온 확인 요청을 서버가 규칙대로 검증한다. 금액이 다르면 승인 API를 부르지 않고 거절하고, 다른 회원의 주문, 사라진 방송·바뀐 소유자, 이미 실패·취소된 주문도 확정하지 않는다. 결제 서비스가 거절하면 실패, 승인 뒤 값이 맞지 않으면 확인 필요로 남기고, 통신이 끊기면 결제 대기로 두어 다시 시도할 수 있다. 결제창에서 취소하거나 실패하면 `/donations/fail` 화면이 서버에 알려 후원을 취소·실패로 바꾸고 결과를 보여 준다. 스펙: `.scratch/donations/spec.md`, 결정: ADR-0007.

02(시작 규칙·화면)와 병행한다. 04(중복 통지)는 이 티켓 다음에 같은 확정 규칙을 다듬는다.

> **변경(2026-11-10, 01 진행 중 사용자 결정)**: 결제창(`payment()`, API 개별 연동 키) 대신 **결제위젯**(`widgets()`, 문서용 공개 키 `test_gck_docs_…`/`test_gsk_docs_…`)을 쓴다. 공식 샘플의 공개 결제창 키가 토스 샌드박스에서 401로 거절되기 때문이다(ADR-0007). 이 문서의 "결제창"은 위젯의 "결제하기"로 이어지는 카드사 테스트 결제 화면을 뜻하고, 후원 시작은 "서버가 주문을 만든다 → 그 금액으로 위젯을 그린다 → 결제하기" 순서다. 위젯은 카드 외 결제수단(간편결제·계좌이체)도 테스트로 보여 주지만 확인은 카드로 한다.

**Blocked by:** 01

**Status:** ready-for-agent

- [ ] 확인 요청 금액이 저장 금액과 다르면 `400`, 후원은 실패, 게이트웨이 승인 호출 0회
- [ ] 다른 회원의 주문 확인 `403`(상태 그대로), 비로그인 `401`, 없는 주문 `404`
- [ ] 방송이 삭제되었거나 소유자가 저장된 방송자와 다르면 `409`, 실패, 승인 호출 0회
- [ ] 실패·취소·확인 필요 주문의 확인 요청 `409`(승인 호출 0회)
- [ ] 게이트웨이가 승인을 거절하면 실패(오류 코드·메시지 저장), 응답에 이유
- [ ] 승인은 완료인데 금액·주문번호가 다르면 확인 필요(적립 안 함), 응답에 이유
- [ ] 게이트웨이 통신 실패면 `502`, 결제 대기 유지, 같은 요청을 다시 보내면 확정된다
- [ ] 각 확인 요청이 통지 기록에 처리 결과(새로 확정·거절)로 남는다
- [ ] `POST /api/donations/fail` JSON `{ orderId, code, message }`: 자기 결제 대기 주문이면 사용자 취소 코드(01에서 확인한 값)는 취소, 그 밖은 실패. 확정된 주문은 바뀌지 않고 `409`, 다른 회원 `403`, 비로그인 `401`
- [ ] 내역·합계에 실패·취소·확인 필요가 들어가지 않는다
- [ ] 백엔드 HTTP API 경계 테스트(가짜 게이트웨이로 각 결과 재현)로 위를 확인한다
- [ ] 프론트: `/donations/fail?code&message&orderId`가 실패 보고를 보내고 취소면 "후원을 취소했습니다", 그 밖은 "후원에 실패했습니다"와 이유, 방송으로 돌아가는 링크
- [ ] 프론트: `/donations/success`에서 서버가 거절하면(400·403·409·502) 이유를 보여 주고, 502는 "다시 확인" 버튼으로 재시도할 수 있다
- [ ] 새 테스트는 새 파일에 둔다. 1~3단계·01 테스트는 모두 green
- [ ] 모든 사이클이 기록되어 있다. 병행 중이라 `docs/tdd-log.md` 대신 이 파일의 `## TDD 기록`에 남기고, 병합할 때 옮긴다
