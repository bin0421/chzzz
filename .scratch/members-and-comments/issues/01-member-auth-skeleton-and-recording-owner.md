# 01: 회원가입·로그인 골격과 녹화방송 소유자

**What to build:** 방문자가 회원가입하면 바로 로그인되고, 헤더에 닉네임과 "로그아웃"이 보인다. 로그아웃·로그인이 되고, 새로고침해도 로그인 상태가 유지된다. 로그인한 회원이 녹화방송을 등록하면 그 회원이 소유자가 되고, 방송 목록과 녹화방송 상세에 소유자 닉네임이 보인다. 비로그인으로 녹화방송 등록 화면에 들어가면 로그인 화면으로 안내되고 로그인 후 돌아오며, API를 직접 불러도 서버가 `401`로 거절한다. 스펙: `.scratch/members-and-comments/spec.md`, 결정: ADR-0005.

02~04가 이 위에서 병행으로 진행되므로 이 티켓에서 공용 기반을 마련한다.
- Spring Security 설정: 세션 기반 인증, BCrypt, 로그인 시 세션 ID 교체, CSRF 토큰 쿠키·헤더, 인증 실패 `401`·권한 부족 `403` Problem Details, MediaMTX 내부 엔드포인트 허용(CSRF 제외)
- Flyway `V3` 하나에 3단계 스키마 전체: 회원, 녹화방송·라이브 방송의 소유자(기존 행은 소유자 없음), 댓글 테이블. 02~04는 새 마이그레이션을 만들지 않는다
- 소유자·작성자 검사 공통 규칙(소유자 없는 방송은 항상 실패)
- "방송 삭제됨" 이벤트(방송 종류 + 식별자): 02·03이 발행하고 04가 받아 댓글을 지운다
- 프론트: 앱 전체 인증 상태, 상태를 바꾸는 요청에 CSRF 헤더를 붙이고 `401`이면 로그인 상태를 비우는 공용 `fetch`, `/login`·`/signup` 화면, 로그인 필요 화면의 `next` 리다이렉트, 헤더

**Blocked by:** None (can start immediately)

**Status:** resolved

- [x] Flyway `V3`가 회원 테이블, 녹화방송·라이브 방송 소유자 칸(nullable), 댓글 테이블을 만든다. `V1`·`V2`는 그대로이고 기존 데이터가 남는다
- [x] `POST /api/auth/signup`: 규칙에 맞으면 `201 { id, nickname }`과 로그인 세션. 아이디(영문 소문자·숫자·`_` 4~20자)·비밀번호(8~64자)·닉네임(공백 제거 1~20자) 위반은 `400`(`errors`), 아이디·닉네임 중복(닉네임은 대소문자·앞뒤 공백 무시)은 `409`(`errors`에 해당 필드)
- [x] `POST /api/auth/login`: 맞으면 `200 { id, nickname }`, 틀리면 `401`과 한 가지 메시지("아이디 또는 비밀번호가 올바르지 않습니다.")
- [x] `GET /api/auth/me`: 로그인 중 `200 { id, nickname }`, 아니면 `401`. CSRF 토큰 쿠키를 내려 준다
- [x] `POST /api/auth/logout`: `204`, 이후 `me`는 `401`
- [x] 비밀번호는 BCrypt 해시로만 저장되고, 어떤 응답에도 아이디·비밀번호 해시가 나오지 않는다
- [x] 세션 쿠키는 `HttpOnly`이고 로그인할 때 세션 ID가 바뀐다
- [x] CSRF 토큰 없이 보낸 상태 변경 요청은 `403`으로 거절된다(테스트)
- [x] `POST /api/recordings`: 비로그인 `401`, 로그인하면 소유자가 기록되고 응답·목록·상세에 `owner: { id, nickname }`. 소유자 없는 기존 녹화방송은 `owner: null`
- [x] MediaMTX 내부 엔드포인트는 인증·CSRF 없이 지금처럼 동작한다(2단계 훅 테스트 green)
- [x] 2단계 라이브 방송 시작은 이 티켓에서 바꾸지 않는다(03 범위). 1·2단계 테스트는 녹화방송 등록에 로그인이 필요해진 만큼만 고쳐 모두 green
- [x] 위 동작이 백엔드 HTTP API 경계 테스트로 검증된다. 테스트는 회원가입·로그인 API를 실제로 불러 받은 세션을 쓴다(`@WithMockUser` 쓰지 않음)
- [x] 프론트: `/signup`·`/login` 화면, 입력란 옆 오류 안내, 가입·로그인 후 `next`(같은 사이트 경로만)로 돌아감
- [x] 프론트: 헤더가 비로그인 "로그인"·"회원가입", 로그인 "닉네임님"·"로그아웃"을 보여 주고 기존 링크는 유지

## Comments

- 인증 경계: Spring Security는 세션 복원과 CSRF 검사만 하고 URL 규칙 없이 모두 통과시킨다. 로그인 필요 여부는 컨트롤러의 `LoginMember` 파라미터(없으면 401, `LoginMember?`면 선택), 소유자·작성자 검사는 서비스의 공통 규칙(`Ownership.requireOwner`)이 맡는다. 02~04가 각자 컨트롤러·서비스만 고치면 되고 보안 설정 파일을 함께 고치지 않아도 된다. 거절 순서 401 → 404 → 403 → 409도 이 구조에서 자연스럽게 나온다.
- 로그인 세션: 가입·로그인 성공 시 기존 세션이 있으면 `changeSessionId`로 ID를 바꾸고 `HttpSessionSecurityContextRepository`에 저장한다. 비밀번호는 `{bcrypt}` 위임 인코더.
- CSRF: `spa()` + 쿠키 저장소(`XSRF-TOKEN`, 자바스크립트가 읽음). 실제 서버에서는 응답 본문을 쓴 뒤라 쿠키가 실리지 않는 경우가 있어, 응답 전에 토큰을 읽는 필터를 더했다. MediaMTX 내부 엔드포인트(`/internal/**`)는 CSRF 검사에서 뺐다.
- 테스트 주의: MockMvc의 `csrf()`는 공유 CSRF 필터의 저장소를 바꿔 두므로, 실제 서버에 요청하는 테스트(쿠키 속성, 413)는 MockMvc와 다른 테스트 클래스에 둔다(`BrowserLikeClient`). 회원 가입 도우미는 `MockMvc.signUp(...)`.
- 02~04용 기반: `Ownership.requireOwner(ownerId, member)`, `BroadcastType`·`BroadcastDeletedEvent`. 01에서는 쓰는 API가 없어 02~04 테스트로 검증한다. 라이브 방송 소유자 칸은 `V3`에 있지만 엔티티 매핑은 03이 한다. 댓글 테이블도 `V3`에 있고 엔티티는 04가 만든다.
- 프론트: `AuthProvider`가 앱 시작 때 `me`로 상태를 정한다. 확인 중에는 로그인 필요 화면을 그대로 그리고, 비로그인이 확인되면 `/login?next=...`로 보낸다. 테스트용 `stubFetch`는 `/api/auth/me` 라우트가 없으면 기본 회원(테스터)으로 로그인된 것으로 응답하고, 비로그인은 `anonymous` 라우트를 넣는다. 요청을 순서로 찾던 기존 테스트 3개는 `requestsTo`로 바꿨다.
- 실제 브라우저 확인(PC, 개발 실행, 2026-11-10): 2단계 데이터가 있는 compose DB는 05의 업그레이드 확인에 남겨 두려고 같은 PostgreSQL에 임시 DB `chzzz_dev3`를 만들어 백엔드(8081)·Vite(5174)로 확인했다. 가입 → 헤더 "방송주인A님", `document.cookie`에는 `XSRF-TOKEN`만 보임(세션 쿠키 HttpOnly) → 외부 URL 등록 → 상세에 소유자 닉네임 → 로그아웃 → 비로그인 `fetch` 등록 401("로그인이 필요합니다."), CSRF 헤더 없는 로그인 403 → `/recordings/new`가 `/login?next=%2Frecordings%2Fnew`로 이동 → 로그인하면 등록 화면으로 돌아옴.
- 결과: 백엔드 105개, 프론트 54개 테스트 green, 빌드·린트 통과.
