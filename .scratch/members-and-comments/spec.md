# 3단계: 회원, 방송 소유자 권한, 댓글

## Problem Statement

지금은 누구나 로그인 없이 녹화방송을 등록하고 라이브 방송을 시작할 수 있다. 그래서 방송이 누구 것인지 알 수 없고, 등록한 사람조차 자기 녹화방송의 제목을 고치거나 지울 방법이 없다. 라이브 방송은 시작한 탭이 들고 있는 송출 키로만 끌 수 있어서, 탭을 닫거나 다른 기기에서는 자기 방송을 제어할 수 없다. 시청자는 방송을 보면서 의견을 남길 곳이 없고, 남기더라도 누가 쓴 글인지, 누가 고치거나 지울 수 있는지 정해져 있지 않다. 남의 방송이나 남의 댓글을 바꾸는 일은 화면에서 버튼을 숨기는 것만으로는 막을 수 없다.

## Solution

2단계 서비스에 **회원**과 **댓글**을 더한다.

- 누구나 아이디·비밀번호·닉네임으로 회원가입하고, 로그인·로그아웃한다. 로그인 상태는 서버 세션 쿠키로 유지된다(ADR-0005).
- 로그인한 회원만 녹화방송을 등록하고 라이브 방송을 시작한다. 등록·시작한 회원이 그 방송의 **소유자**가 된다.
- 소유자만 방송의 제목을 수정하고 방송을 삭제하며, 라이브 방송을 종료한다. 서버가 매 요청마다 세션의 회원이 소유자인지 검사한다. 송출 키는 MediaMTX 송출 허가에만 남는다(ADR-0006).
- 로그인한 회원은 녹화방송과 라이브 방송에 **댓글**을 쓴다. 댓글 목록은 누구나 본다. 댓글은 **작성자**만 수정·삭제한다.
- 방송 목록 조회와 시청은 지금처럼 로그인 없이 누구나 한다. README에 공개 범위를 적는다.
- 1·2단계 기능은 그대로 동작한다. 회원 기능 이전에 만들어진 방송은 소유자 없이 남아 누구나 시청할 수 있지만 아무도 수정·삭제할 수 없다.

## User Stories

### 회원가입·로그인·로그아웃

1. 방문자로서, 아이디·비밀번호·닉네임을 입력해 회원가입하고 싶다. 그래야 방송을 등록하고 댓글을 쓸 수 있다.
2. 방문자로서, 회원가입하면 바로 로그인된 상태가 되고 싶다. 그래야 가입 후 다시 로그인하지 않아도 된다.
3. 방문자로서, 아이디가 규칙(영문 소문자·숫자·`_` 4~20자)에 맞지 않으면 가입 화면에서 바로 이유를 알고 싶다.
4. 방문자로서, 이미 쓰는 아이디로 가입하려 하면 "이미 사용 중인 아이디입니다" 같은 안내를 아이디 입력란 옆에서 보고 싶다.
5. 방문자로서, 비밀번호가 8~64자가 아니면 안내를 보고 싶다.
6. 방문자로서, 닉네임이 비었거나 20자를 넘으면 안내를 보고 싶다.
7. 방문자로서, 다른 회원이 쓰는 닉네임(대소문자·앞뒤 공백만 다른 것 포함)으로는 가입할 수 없고 그 이유를 알고 싶다. 그래야 화면의 닉네임만 보고 사람을 구분할 수 있다.
8. 회원으로서, 아이디와 비밀번호로 로그인하고 싶다.
9. 회원으로서, 아이디나 비밀번호가 틀리면 어느 쪽이 틀렸는지 드러내지 않는 한 가지 안내("아이디 또는 비밀번호가 올바르지 않습니다.")를 보고 싶다.
10. 회원으로서, 헤더에서 내 닉네임과 로그아웃 버튼을 보고 싶다. 그래야 지금 로그인되어 있는지 안다.
11. 회원으로서, 로그아웃하면 서버의 로그인 상태가 끝나고 헤더가 다시 "로그인"·"회원가입"으로 바뀌었으면 한다.
12. 방문자로서, 헤더에서 "로그인"과 "회원가입"으로 바로 갈 수 있으면 한다.
13. 방문자로서, 로그인이 필요한 화면(녹화방송 등록, 라이브 방송 시작)에 들어가면 로그인 화면으로 안내되고, 로그인하거나 가입한 뒤 원래 화면으로 돌아오고 싶다.
14. 회원으로서, 새로고침하거나 다른 탭을 열어도 로그인 상태가 유지되었으면 한다.
15. 회원으로서, 내 비밀번호가 서버에 원문으로 저장되지 않기를 바란다.

### 방송 소유자와 권한

16. 회원으로서, 녹화방송을 등록하면 내가 그 녹화방송의 소유자가 되었으면 한다.
17. 회원으로서, 라이브 방송을 시작하면 내가 그 라이브 방송의 소유자가 되었으면 한다.
18. 방문자로서, 로그인하지 않고 녹화방송 등록이나 라이브 방송 시작을 요청하면(화면을 거치지 않고 API를 직접 불러도) 서버가 거절했으면 한다.
19. 시청자로서, 방송 목록과 상세·시청 화면에서 그 방송 소유자의 닉네임을 보고 싶다.
20. 소유자로서, 내 녹화방송 상세 화면에서 제목을 수정하고 싶다.
21. 소유자로서, 내 녹화방송을 삭제하고 싶다. 업로드 파일과 댓글도 함께 지워졌으면 한다.
22. 소유자로서, 내 라이브 방송 시청 화면에서 제목을 수정하고 싶다(대기·방송 중·종료 모두).
23. 소유자로서, 내 라이브 방송을 송출하던 탭이 아니라도(다른 탭, 다른 기기) 로그인만 되어 있으면 "방송 종료"로 끝내고 싶다.
24. 소유자로서, 종료된 내 라이브 방송을 삭제하고 싶다. 댓글도 함께 지워졌으면 한다.
25. 소유자로서, 대기·방송 중인 라이브 방송을 삭제하려 하면 먼저 종료하라는 안내를 받고 싶다.
26. 다른 회원으로서, 남의 방송에는 수정·삭제·종료 버튼이 보이지 않았으면 한다.
27. 서비스 운영자로서, 다른 회원이나 비로그인 사용자가 API를 직접 불러 남의 방송을 수정·삭제·종료하려 하면 서버가 거절했으면 한다(비로그인 401, 다른 회원 403).
28. 서비스 운영자로서, 회원 기능 이전에 만들어진 소유자 없는 방송은 누구도 수정·삭제·종료할 수 없었으면 한다.
29. 송출자로서, 라이브 방송을 시작하면 그 방송에만 쓸 수 있는 송출 키를 받아 휴대폰에서 바로 송출하고 싶다(2단계와 같은 경험).
30. 서비스 운영자로서, 송출 키가 새어 나가도 그것으로 방송을 종료하거나 바꿀 수는 없었으면 한다.
31. 송출자로서, 2단계처럼 휴대폰 카메라·마이크로 송출하고, 종료·끊김·대기 시간 초과·재시작 정리가 그대로 동작했으면 한다.

### 댓글

32. 시청자로서, 녹화방송 상세 화면과 라이브 방송 시청 화면 아래에서 그 방송의 댓글 목록을 오래된 순으로 보고 싶다.
33. 방문자로서, 로그인하지 않아도 댓글 목록은 볼 수 있었으면 한다.
34. 회원으로서, 방송에 댓글을 쓰고 싶다. 쓴 댓글은 바로 목록에 나타났으면 한다.
35. 시청자로서, 각 댓글의 작성자 닉네임과 작성 시각을 보고 싶다.
36. 방문자로서, 댓글 작성란 대신 "로그인하면 댓글을 쓸 수 있습니다"와 로그인 링크를 보고 싶다.
37. 서비스 운영자로서, 로그인하지 않은 요청으로 댓글을 쓰면(API 직접 호출 포함) 서버가 401로 거절했으면 한다.
38. 회원으로서, 빈 댓글이나 500자를 넘는 댓글은 등록되지 않고 이유를 보고 싶다.
39. 작성자로서, 내 댓글을 수정하고 싶다. 수정한 댓글에는 "수정됨"이 표시되었으면 한다.
40. 작성자로서, 내 댓글을 삭제하고 싶다.
41. 다른 회원으로서, 남의 댓글에는 수정·삭제 버튼이 보이지 않았으면 한다. 방송 소유자라도 남의 댓글은 지울 수 없다.
42. 서비스 운영자로서, 작성자가 아닌 회원이 API로 남의 댓글을 수정·삭제하려 하면 403, 비로그인이면 401로 거절했으면 한다.
43. 시청자로서, 라이브 방송을 보는 동안 다른 사람이 쓴 댓글이 몇 초 안에 목록에 나타났으면 한다.
44. 시청자로서, 종료된 라이브 방송에도 댓글을 남기고 볼 수 있었으면 한다.
45. 시청자로서, 없는 방송의 댓글을 요청하면 "찾을 수 없음"이 나왔으면 한다.

### 보안과 운영

46. 서비스 운영자로서, 다른 사이트가 로그인한 회원의 브라우저를 이용해 방송을 지우거나 댓글을 쓰는 요청 위조(CSRF)를 막고 싶다.
47. 서비스 운영자로서, 세션 쿠키를 자바스크립트가 읽을 수 없었으면 한다(`HttpOnly`).
48. 서비스 운영자로서, 응답 어디에도 비밀번호 해시나 다른 회원의 아이디, 송출 키 해시가 나오지 않았으면 한다.
49. 채점자로서, README에서 누가 무엇을 할 수 있는지(공개 범위)와 비로그인·소유자·다른 회원별 허용·거절 확인 절차를 보고 싶다.
50. 채점자로서, `docker compose up --build`만으로 회원·댓글까지 포함된 서비스를 띄우고, 1·2단계 직접 확인 절차도 그대로 통과하기를 바란다.
51. 개발자로서, 기존 데이터가 남아 있는 DB에 새 마이그레이션만 적용해 3단계로 올릴 수 있었으면 한다.

## Implementation Decisions

### 모듈

- **회원 모듈(새로)**: 회원 엔티티(아이디, 비밀번호 해시, 닉네임, 가입 시각), 가입 규칙, 로그인·로그아웃·현재 회원 조회 API.
- **보안 설정(새로)**: Spring Security. 세션 기반 인증, BCrypt 비밀번호 해시, 로그인 시 세션 ID 교체, CSRF 토큰 쿠키(`XSRF-TOKEN`, 자바스크립트가 읽을 수 있음)와 요청 헤더(`X-XSRF-TOKEN`) 검사. 인증 실패는 로그인 화면 리다이렉트가 아니라 `401` Problem Details, 권한 부족은 `403` Problem Details.
- **녹화방송 모듈(변경)**: 소유자 추가, 등록에 로그인 필요, 제목 수정·삭제 추가.
- **라이브 방송 모듈(변경)**: 소유자 추가, 시작에 로그인 필요, 종료를 송출 키 대신 소유자 검사로, 제목 수정·삭제 추가. 송출 허가·훅·대기 시간 초과·재시작 정리는 그대로.
- **댓글 모듈(새로)**: 댓글 엔티티, 방송별 목록·작성·수정·삭제 API.
- **소유자 검사**: "세션의 회원 == 방송의 소유자(또는 댓글의 작성자)"를 서비스 계층에서 검사한다. 녹화방송·라이브 방송·댓글이 같은 규칙을 쓰도록 공통으로 둔다. 소유자가 없는 방송은 항상 실패한다.
- **프론트 인증 상태**: 앱 시작 시 현재 회원을 불러와 앱 전체에서 쓴다. 공용 `fetch` 함수가 상태를 바꾸는 요청에 CSRF 헤더를 붙이고, `401`을 받으면 로그인 상태를 비운다.

### 스키마 (Flyway `V3`, 기존 데이터 유지)

- `member`: `id`, `login_id`(소문자, 유니크), `password_hash`, `nickname`, `nickname_key`(앞뒤 공백 제거 + 소문자, 유니크), `created_at`.
- `recording`, `live_broadcast`에 `owner_id`(nullable, `member` 참조) 추가. 기존 행은 `NULL`(소유자 없음).
- `comment`: `id`, `broadcast_type`(`RECORDING`/`LIVE_BROADCAST`), `broadcast_id`, `author_id`(`member` 참조), `content`, `created_at`, `updated_at`(수정 전에는 `NULL`). (`broadcast_type`, `broadcast_id`, `created_at`) 인덱스. 방송을 삭제할 때 서비스가 그 방송의 댓글도 함께 지운다.

### 회원 규칙

- 아이디: 앞뒤 공백 제거 후 영문 소문자·숫자·`_` 4~20자. 중복 불가.
- 비밀번호: 8~64자. 공백 제거하지 않음. BCrypt 해시로만 저장.
- 닉네임: 앞뒤 공백 제거 후 1~20자. 대소문자를 무시하고 비교해 중복 불가(DB 유니크 제약으로 동시 가입도 막음).
- 가입 성공 시 바로 로그인 세션을 만든다.
- 로그인 실패 메시지는 하나: "아이디 또는 비밀번호가 올바르지 않습니다."
- 세션은 백엔드 메모리. 재시작하면 로그아웃된다.

### API 계약

인증 (`/api/auth`):

| 메서드 | 경로 | 인증 | 설명 |
| --- | --- | --- | --- |
| `GET` | `/api/auth/me` | 공개 | 로그인 중이면 `200 { id, nickname }`, 아니면 `401`. CSRF 토큰 쿠키도 이때 내려 준다 |
| `POST` | `/api/auth/signup` | 공개 | JSON `{ loginId, password, nickname }`. `201 { id, nickname }` + 로그인 세션. 검증 실패 `400`(`errors`), 아이디·닉네임 중복 `409`(`errors`에 해당 필드) |
| `POST` | `/api/auth/login` | 공개 | JSON `{ loginId, password }`. `200 { id, nickname }`, 실패 `401` |
| `POST` | `/api/auth/logout` | 로그인 | 세션 종료, `204` |

방송 (기존 응답에 `owner: { id, nickname } | null` 추가):

| 메서드 | 경로 | 인증 | 설명 |
| --- | --- | --- | --- |
| `POST` | `/api/recordings` | 로그인 | 기존과 같고, 소유자를 기록 |
| `PATCH` | `/api/recordings/{id}` | 소유자 | JSON `{ title }`. `200` 상세 |
| `DELETE` | `/api/recordings/{id}` | 소유자 | `204`. 업로드 파일·댓글도 삭제 |
| `POST` | `/api/live-broadcasts` | 로그인 | 기존과 같고, 소유자를 기록. 송출 키는 이 응답에만 |
| `POST` | `/api/live-broadcasts/{id}/end` | 소유자 | 송출 키 헤더 대신 세션으로 검사. 이미 종료 `409` |
| `PATCH` | `/api/live-broadcasts/{id}` | 소유자 | JSON `{ title }`. 모든 상태에서 가능 |
| `DELETE` | `/api/live-broadcasts/{id}` | 소유자 | 종료된 방송만 `204`(댓글도 삭제). 대기·방송 중이면 `409` |

조회(`GET` 목록·상세·영상, WHEP 시청)는 모두 공개로 유지한다.

댓글:

| 메서드 | 경로 | 인증 | 설명 |
| --- | --- | --- | --- |
| `GET` | `/api/recordings/{id}/comments`, `/api/live-broadcasts/{id}/comments` | 공개 | 오래된 순 전체. `[{ id, content, author: { id, nickname }, createdAt, updatedAt }]`. 방송 없음 `404` |
| `POST` | 위와 같은 경로 | 로그인 | JSON `{ content }`. `201` 댓글 |
| `PATCH` | `/api/comments/{id}` | 작성자 | JSON `{ content }`. `200` 댓글(`updatedAt` 채워짐) |
| `DELETE` | `/api/comments/{id}` | 작성자 | `204` |

- 댓글 내용: 앞뒤 공백 제거 후 1~500자. 위반 시 `400`(`errors`에 `content`).
- 거절 규칙(모든 상태 변경 API 공통): 비로그인 `401` → 대상 없음 `404` → 소유자·작성자 아님 `403` → 상태 충돌 `409`. 모두 Problem Details. CSRF 토큰이 없거나 틀리면 `403`.
- MediaMTX 내부 엔드포인트(`/internal/mediamtx/*`)는 Spring Security에서 인증 없이 허용하되 2단계처럼 Caddy·nginx가 바깥에서 404로 막는다. CSRF 검사에서도 제외한다.
- 응답에는 회원의 `id`와 `nickname`만 나온다. 아이디·비밀번호 해시는 나오지 않는다.

### 화면

- 새 화면: `/signup`(아이디·비밀번호·닉네임), `/login`(아이디·비밀번호). 둘 다 `next` 쿼리로 돌아갈 화면을 받는다(같은 사이트 경로만 허용).
- 헤더: 비로그인 "로그인"·"회원가입", 로그인 "닉네임님"·"로그아웃". 기존 링크(목록·방송 시작·녹화방송 등록)는 유지한다.
- 로그인이 필요한 화면(`/recordings/new`, `/live/new`)은 비로그인이면 `/login?next=...`로 보낸다.
- 방송 목록·상세·시청 화면에 소유자 닉네임. 소유자 없으면 표시하지 않는다.
- 소유자에게만 보이는 관리 버튼: 녹화방송 상세 "수정"(제목 인라인 수정)·"삭제"(확인 후 목록으로), 라이브 시청 화면 "제목 수정"·"방송 종료"(대기·방송 중)·"삭제"(종료 후).
- 송출 화면: 종료는 세션으로 하므로 2단계의 탭 저장소(sessionStorage) 송출 키 보관과 "이 탭에서 시작한 라이브 방송" 재개 표시를 없앤다. 송출 중 "방송 종료"는 그대로.
- 댓글 영역: 녹화방송 상세와 라이브 시청 화면 아래. 목록(닉네임, 시각, "수정됨"), 로그인 시 작성란, 비로그인 시 로그인 안내 링크. 작성자에게만 "수정"·"삭제". 라이브 방송 댓글은 3초마다 다시 불러온다.
- 서버가 `401`을 주면 로그인 안내, `403`이면 권한 없음 안내를 보여 준다. 버튼을 숨기는 것은 보조이고 서버 검사가 기준이다.

## Testing Decisions

- 좋은 테스트는 외부 동작만 본다. 백엔드는 HTTP 요청·응답(상태 코드, 본문, 그 뒤의 조회 결과), 프론트는 사용자가 보는 화면과 서버로 나간 요청만 확인하고 내부 구현(서비스 메서드, 상태 변수)을 직접 부르지 않는다.
- **백엔드: HTTP API 경계 하나** (prior art: `RecordingApiTest`, `LiveBroadcastApiTest`, `LiveBroadcastEndApiTest`, `MediaMtxHookApiTest`).
  - Spring Boot 앱 전체 + Testcontainers PostgreSQL + MockMvc.
  - 로그인: 테스트도 회원가입·로그인 API를 실제로 불러 받은 세션으로 다음 요청을 보낸다. 가짜 인증 사용자(`@WithMockUser`)는 쓰지 않는다.
  - CSRF: 대부분 `spring-security-test`의 `csrf()`로 토큰을 붙이고, 토큰 없이 보낸 요청이 거절되는 테스트를 따로 둔다.
  - 권한: 상태를 바꾸는 API마다 비로그인·소유자(작성자)·다른 회원 세 경우를 보내 `401`·`2xx`·`403`을 확인하고, 거절 뒤 대상이 바뀌지 않았는지 조회로 확인한다. 소유자 없는 기존 방송도 확인한다.
  - MediaMTX 훅은 계속 테스트가 내부 엔드포인트를 직접 불러 흉내 내고, 시간은 바꿔 끼우는 `Clock`을 쓴다.
  - 1·2단계 테스트는 등록·시작에 로그인이 필요해진 만큼만 고쳐서 계속 green이어야 한다.
- **프론트: 앱 화면 단위** (prior art: `LiveBroadcast*.test.tsx`, `Recording*.test.tsx`, `renderApp`, `createFakeMediaAdapter`).
  - 라우터 포함 앱 전체를 렌더링하고 `fetch`와 미디어 어댑터만 가짜로 바꾼다.
  - 로그인 상태는 스텁한 `/api/auth/me` 응답으로 만든다(별도 이음새 없음).
  - CSRF: 테스트가 토큰 쿠키를 넣어 두고 상태를 바꾸는 요청에 `X-XSRF-TOKEN` 헤더가 실리는지 확인한다.
  - 소유자·작성자·다른 회원·비로그인별로 버튼이 보이고 숨는지, 서버의 `401`·`403`에 맞는 안내가 나오는지 확인한다.
- E2E 자동화는 하지 않고 README 직접 확인 절차로 대신한다. 직접 확인은 브라우저 두 개(또는 일반·시크릿 창)로 비로그인·소유자·다른 회원을 나눠 화면과 API 직접 호출(버튼을 숨겨도 서버가 거절하는지) 모두 확인한다.

## Out of Scope

- 이메일 인증, 비밀번호 찾기·변경, 회원 정보 수정, 회원 탈퇴

- 소셜 로그인, JWT, 재시작 후 로그인 유지(Spring Session)

- 도네이션(4단계)
- E2E 자동화 테스트

## Further Notes

- 결정 근거: ADR-0005(세션 쿠키 + Spring Security + CSRF), ADR-0006(송출 키는 송출 허가 전용). 2단계 ADR-0003·0004는 그대로 유효하다.
- 휴대폰(`https://<PUBLIC_HOST>:8443`)과 PC(`http://localhost:3000`)는 출처가 달라서 로그인도 각각 따로 한다. 세션 쿠키는 HTTP 접속도 지원해야 하므로 `Secure` 속성을 강제하지 않는다.
- 2단계 송출 화면의 송출 키 보관(sessionStorage)과 그 테스트는 이번에 없어지는 동작이므로, 해당 테스트는 새 동작(소유자 세션으로 종료)에 맞게 바꾼다.
- 1·2단계에서 쓰던 직접 확인용 데이터(소유자 없음)는 `V3` 적용 뒤에도 남아 시청할 수 있어야 한다.
