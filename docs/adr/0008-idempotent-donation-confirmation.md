# 같은 결제의 승인 통지는 몇 번 와도 후원을 한 번만 확정한다

승인 통지는 두 경로로, 같은 결제에 대해 여러 번 올 수 있다. 결제 후 돌아온 화면의 확인 요청(새로고침·재전송)과 토스 웹훅(재전송)이다. 후원 확정은 다음 세 겹으로 한 번만 일어나게 한다.

1. **멱등 처리**: 이미 같은 결제 키로 확정된 후원이면 토스를 다시 부르지 않고 기존 결과를 그대로 돌려준다(새로 적립하지 않음).
2. **저장 구조**: 주문번호와 결제 키에 유니크 제약을 건다. 확정할 때는 주문 행을 잠가(`SELECT … FOR UPDATE`) 동시에 온 통지도 한 건만 확정하게 한다.
3. **결제 서비스를 기준으로**: 웹훅 본문은 믿지 않는다. 받은 결제 키로 토스 조회 API를 다시 불러 실제 상태를 확인하고 같은 규칙으로 처리한다. 승인은 끝났는데 서버가 확정하기 전에 응답이 끊긴 경우도, 다음 통지에서 조회 결과로 확정된다.

모든 통지는 통지 기록 테이블에 한 줄씩 남는다(결제 키, 출처, 받은 시각, 처리 결과: 새로 확정·이미 확정·무시·거절). 같은 통지가 두 번 와서 두 번째가 "이미 확정"으로 끝났다는 것을 이 기록으로 보여 줄 수 있다.

## Considered Options

- **화면의 확인 요청만 받기(웹훅 없음)**: 단순하지만 사용자가 결제 직후 창을 닫으면 적립되지 않는다.
- **웹훅 본문의 상태를 그대로 믿기**: 누구나 같은 모양의 요청을 보낼 수 있어서 위조된 통지로 적립될 수 있다.
- **웹훅 서명 검증**: 토스는 `tosspayments-webhook-signature` 헤더로 HMAC 서명을 주지만, 검증에 필요한 보안 키는 각자의 개발자센터 계정에 발급된다. 채점자가 가입 없이 쓰는 공개 테스트 키 세트에는 보안 키가 없어서 쓸 수 없다. 조회 API 재확인은 서명이 없어도 위조를 막는다.
- **애플리케이션 코드의 중복 확인만**: 동시에 두 통지가 오면 둘 다 "아직 확정 안 됨"을 보고 두 번 적립할 수 있다.

## Consequences

- 토스는 로컬 PC로 웹훅을 보낼 수 없다(공개 주소가 아님). 웹훅 엔드포인트는 만들어 두지만, 직접 확인에서는 같은 통지를 `curl`로 두 번 보내 합계가 한 번만 늘어나는지 확인한다.
- 웹훅 엔드포인트는 로그인·CSRF 없이 열려 있다. 본문 대신 조회 API를 믿으므로 위조 요청은 "무시"로 끝난다.
