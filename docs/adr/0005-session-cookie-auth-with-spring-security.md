# 로그인 상태는 Spring Security의 서버 세션 쿠키로 유지하고 CSRF 토큰으로 막는다

회원가입·로그인·로그아웃을 Spring Security로 구현한다. 로그인하면 서버가 세션을 만들고 브라우저는 `HttpOnly` 세션 쿠키만 가진다. 프론트(SPA)와 API는 nginx·Caddy·Vite 프록시 뒤의 같은 출처라서 쿠키가 그대로 오간다. 쿠키는 브라우저가 자동으로 붙이므로 다른 사이트의 요청 위조(CSRF)를 막기 위해 Spring Security의 CSRF 토큰을 `XSRF-TOKEN` 쿠키로 내려 주고, 프론트 `fetch`가 상태를 바꾸는 요청마다 `X-XSRF-TOKEN` 헤더에 실어 보낸다. 비밀번호는 BCrypt 해시로만 저장한다. 세션은 백엔드 메모리에 두므로 백엔드를 재시작하면 모두 로그아웃된다.

## Considered Options

- **JWT(Authorization 헤더)**: 서버가 상태를 갖지 않지만, 로그아웃해도 이미 발급한 토큰을 무효로 만들기 어렵고 토큰을 브라우저 어디에 둘지(XSS에 노출되는 저장소) 정해야 한다. 같은 출처 SPA에서는 얻는 것이 적다.
- **인증을 직접 구현**: 의존성이 줄지만 비밀번호 해시, 로그인 시 세션 ID 교체(세션 고정 방지), CSRF 방어를 직접 챙겨야 한다.
- **Spring Session JDBC**: 재시작해도 로그인이 유지되지만 의존성과 세션 테이블이 늘어난다. 과제 범위에서는 재시작 시 다시 로그인하는 것으로 충분하다.

## Consequences

- 상태를 바꾸는 모든 요청(등록·업로드·시작·종료·수정·삭제·댓글)에 CSRF 헤더가 필요하다. API를 직접 호출해 확인할 때도 먼저 토큰 쿠키를 받아야 한다.
- 비로그인은 `401`, 로그인했지만 소유자·작성자가 아니면 `403`으로 구분해 응답한다(Problem Details).
- 백엔드가 여러 대가 되면 세션 공유가 필요하다(범위 밖).
