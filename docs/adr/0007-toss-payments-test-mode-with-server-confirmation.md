# 후원 결제는 토스페이먼츠 테스트 모드로 하고, 서버가 승인을 확인한 뒤에만 확정한다

후원 결제는 토스페이먼츠 **결제위젯**(주문서형)의 테스트 모드를 쓴다. 토스 문서와 공식 샘플에 공개된 문서용 결제 키(`test_gck_docs_…`/`test_gsk_docs_…`)로 가입 없이 동작해서 채점자가 그대로 돌려 볼 수 있다. 위젯은 우리 페이지 안에 결제수단 목록과 약관 동의를 그리고("테스트 환경이에요. 실제로 결제되지 않아요."), 결제하기를 누르면 카드사 테스트 결제창으로 이어진다. 성공·실패·취소를 모두 만들 수 있고 실제 돈은 움직이지 않는다.

후원은 서버가 먼저 **결제 대기**로 만든다. 주문번호와 금액, 방송자(그 순간의 방송 소유자)를 서버가 정해 저장하고, 결제창에는 그 주문번호와 금액만 넘긴다. 결제 후 성공 주소로 돌아온 화면이 결제 키·주문번호·금액을 서버에 보내면, 서버는 다음을 모두 확인한 뒤에만 후원을 **확정**한다.

1. 주문이 이 회원의 결제 대기 주문인지
2. 금액이 저장한 금액과 같은지
3. 방송자가 여전히 그 방송의 소유자인지
4. 위가 맞을 때만 토스 승인 API를 부르고, 응답이 완료(`DONE`)이며 금액·주문번호가 일치하는지

화면에 "성공"이 떴다는 사실이나 주소창의 금액은 믿지 않는다. 금액이 다르면 승인 API를 부르지 않으므로 결제가 승인되지 않는다. 위젯 금액은 서버가 후원을 만든 뒤 돌려준 금액으로만 정한다. 토스 호출은 백엔드가 라이브러리 없이 REST로 하고(승인 API는 결제창과 같다), 프론트는 공식 SDK(npm, 버전 고정)로 위젯만 그린다. 클라이언트 키는 빌드에 넣지 않고 서버가 내려 준다.

## Considered Options

- **결제창(API 개별 연동 키, `payment().requestPayment`)**: 처음에 고른 방식. 결제창은 `test_ck_` 키만 받는데, 공식 샘플의 공개 `test_ck_` 키를 토스 샌드박스가 `401 UNAUTHORIZED_KEY`로 거절해 가입 없이는 쓸 수 없었다(2026-11-10 확인). 개발자센터에 가입해 받은 내 테스트 키를 쓰면 되지만, 채점자도 가입하거나 시크릿 키를 저장소에 올려야 한다.

- **Stripe 테스트 모드**: 널리 쓰이지만 계정을 만들어 키를 받아야 하고, 원화 소액 후원이라는 과제 맥락과 거리가 있다.
- **PortOne(아임포트)**: 여러 결제사를 묶어 주지만 층이 하나 더 생기고 채널 설정이 필요하다.
- **직접 만든 가짜 결제 서버**: 인터넷 없이 돌지만 "결제 서비스의 테스트·샌드박스 모드" 요구를 채우지 못한다.

## Consequences

- 후원 확인에는 PC(백엔드 컨테이너 포함)와 브라우저의 인터넷 연결이 필요하다. 1~3단계 기능은 인터넷 없이도 동작한다.
- 테스트에서는 토스를 부를 수 없으므로 백엔드는 결제 게이트웨이(승인·조회) 경계를, 프론트는 결제창 어댑터 경계를 두고 가짜로 바꾼다. 실제 샌드박스 연동은 README 직접 확인 절차로 확인한다.
- 승인 뒤에 금액이 맞지 않는 이상 상황은 확정하지 않고 확인이 필요한 상태로 남긴다. 자동 결제 취소(환불)는 다루지 않는다.
