# 발표 노트

6단계까지 끝난 최종본으로 PPT를 만들 때 쓸 재료를 단계마다 쌓아 둔다. 슬라이드 문장이 아니라 사실·결정·수치·스크린샷 위치를 적는다. 근거 문서는 링크로 가리키고 내용을 복사하지 않는다.

- 결정 근거: `docs/adr/`
- TDD 과정: `docs/tdd-log.md`
- 용어: `GLOSSARY.md`
- 단계별 상태: git 태그 `stage-1` ~ `stage-5` (`stage-6`은 사용자가 요청할 때 붙인다. GitHub Release `stage-6`이 같은 태그를 쓴다)

## 1단계: 녹화방송 등록·시청

### 목표
- 로그인 없이 녹화방송(업로드 파일 또는 외부 URL)을 등록하고 목록·상세·플레이어로 시청한다. 재시작 후에도 남는다.

### 주요 결정
- 프론트 React + Vite + TS(SPA)와 백엔드 Spring Boot + Kotlin REST API 분리
- PostgreSQL + Flyway: 4단계에 걸친 스키마 변경을 버전으로 관리
- 업로드 파일은 로컬 디스크 + Range 스트리밍 (ADR-0001)
- 외부 URL은 서버에서 접속 확인하지 않음 (ADR-0002)
- 영상 출처를 "종류 + 값"으로 모델링해서 2단계 출처 추가에 대비
- 등록자(소유자)는 3단계로 미룸
- Spring Boot 3.x로 정했으나 Initializr가 3.x를 더 이상 제공하지 않고 3.5 무료 지원도 끝나 4.1.2로 변경
- 테스트 경계는 두 개뿐: 백엔드 HTTP API(Testcontainers 실제 PostgreSQL), 프론트 앱 화면 단위(`fetch`만 스텁)
- 티켓을 수직 슬라이스 6개로 나누고, 골격(01) 이후 02~05를 별도 worktree에서 병행 개발한 뒤 병합

### 결과·수치
- 테스트: 백엔드 26개, 프론트 19개, 모두 green (커버리지는 측정하지 않음)
- TDD 사이클 43개 기록 (`docs/tdd-log.md`): 01 7개, 02 14개, 03 15개, 04 7개. 05(Compose)는 설정 작업이라 TDD 대상 아님
- 직접 확인 절차 7단계를 깨끗한 환경의 `docker compose up --build`에서 모두 통과 (README "직접 확인 절차")
- 스크린샷: `docs/screenshots/stage-1/` (빈 목록, 등록 폼, 외부 URL 재생, 업로드 재생·탐색, 목록, 입력 오류 2종)

### 어려웠던 점·배운 점
- **브라우저 확인에서 찾은 버그**: 등록 응답의 등록일시(나노초)와 DB에 저장된 값(PostgreSQL이 마이크로초로 반올림)이 달랐다. 단위 테스트만으로는 놓쳤을 문제로, 실패하는 테스트를 먼저 쓰고 마이크로초로 잘라 해결 (tdd-log #7)
- **처음부터 green인 테스트의 민감도 확인**: Range 요청(206/416)은 Spring MVC가 이미 처리해서 처음부터 통과했다. 테스트가 의미 있는지 확인하려고 구현을 잠시 바꿔 실패하는 것을 눈으로 확인 (tdd-log #35, #36)
- **MockMvc의 한계**: MockMvc는 multipart 크기 한도를 적용하지 않아서 413 테스트만 실제 포트로 요청
- **설정 형식 차이**: nginx `client_max_body_size`는 Spring의 `500MB` 형식을 받지 않아, 시작 스크립트가 같은 환경변수를 nginx 형식으로 바꾸게 함
- **병행 개발과 병합**: 공유 파일 충돌을 줄이려고 새 테스트는 새 파일에, TDD 기록은 티켓 파일에 따로 남긴 뒤 병합할 때 합쳤다. 결과적으로 02·04·05는 충돌 없이, 03은 main을 먼저 받아 자기 브랜치에서 충돌을 해결한 뒤 병합
- **로컬 포트 충돌**: 8080을 다른 앱이 써서 백엔드 포트(`SERVER_PORT`)와 Vite 프록시 대상(`VITE_API_PROXY_TARGET`), Compose 호스트 포트(`APP_PORT`, 기본 3000)를 모두 환경변수로 뺌
- **남은 개선점**: 등록 폼에는 스타일이 거의 없다(목록·상세만 기본 CSS). 기능 요구사항은 충족하지만 발표 전 다듬을 후보

## 2단계: 라이브 방송 송출

### 목표
- 휴대폰 카메라·마이크로 라이브 방송을 시작·종료하고, 시청자가 방송 목록에서 골라 다른 화면에서 실시간으로 본다. 방송 중·종료를 구분해 표시한다. 로그인 없이, 1단계 기능은 그대로 둔다.

### 주요 결정
- 송출·시청 방식: WebRTC WHIP/WHEP + MediaMTX (ADR-0003). HLS(지연 5~10초)·직접 구현(SFU) 대신 지연이 작고 표준 프로토콜인 쪽. 대가로 같은 LAN 한정(TURN 없음)
- 휴대폰 HTTPS: Caddy 로컬 CA로 LAN IP 인증서 발급 (ADR-0004). 카메라는 보안 컨텍스트에서만 열리기 때문. 대가로 휴대폰에서 인증서 경고를 한 번 넘겨야 함
- 로그인 없는 종료 권한: 방송마다 송출 키를 한 번만 발급하고 해시만 저장. 송출 허가와 종료 API 모두 이 키로 확인
- MediaMTX는 미디어만 다루고 판단은 백엔드가: 송출·시청 허가(HTTP 인증)와 영상 들어옴·끊김 훅을 백엔드 내부 엔드포인트로 받음. `/internal`은 Caddy·nginx에서 바깥에 404
- 상태 모델: 대기 → 방송 중 → 종료. 대기를 둔 이유는 "시작했지만 영상이 아직 안 옴"을 목록에서 숨기고, 60초 안에 오지 않으면 정리하려고. 서비스 재시작 때 남은 대기·방송 중도 종료로 정리
- 목록·시청 화면 갱신은 폴링(목록 5초, 시청 3초). 웹소켓 없이 요구사항(상태 구분 표시)을 충족
- 테스트 경계는 1단계와 같은 두 개 + 이음새 둘: MediaMTX 훅은 테스트가 내부 엔드포인트를 직접 호출, 시간은 바꿔 끼우는 `Clock`, 프론트는 미디어 어댑터(카메라·WebRTC)만 가짜
- 1단계와 같은 진행: 골격 티켓(01) 뒤 02~05를 worktree 4개에서 병행, 06에서 병합 후 휴대폰으로 직접 확인

### 결과·수치
- 테스트: 백엔드 77개(1단계 26 + 51), 프론트 45개(1단계 19 + 26), 모두 green
- TDD 사이클 45개 기록 (`docs/tdd-log.md` #44~#88): 01 10개, 02 14개, 03 10개, 04 11개. 05(Caddy·Compose)는 설정 작업이라 TDD 대상 아님
- 휴대폰 직접 확인(Android Chrome 송출 → PC Chrome 시청): 세로 720×1280 영상 + 소리, 지연은 체감상 거의 없음. 종료 버튼 → PC 시청 화면·목록이 몇 초 안에 종료로 바뀜. 탭 닫기 → MediaMTX가 끊김을 알아챈 약 30초 뒤 자동 종료
- 재시작 후 라이브 방송 기록 유지, 남은 대기는 종료로 정리. 1단계 확인 절차도 같은 실행에서 다시 통과
- 스크린샷: `docs/screenshots/stage-2/` (PC 목록 방송 중, 시청 재생, 시청 종료, 목록 종료). 휴대폰 화면은 기기 문제로 캡처하지 못함

### 어려웠던 점·배운 점
- **개발 PC에 카메라가 없음**: 01 골격 확인은 `getUserMedia`를 캔버스+사인파 합성 스트림으로 바꾸고, 서버 경로는 ffmpeg WHIP 송출로 확인. 실제 카메라는 마지막에 휴대폰으로 확인. 미디어 어댑터를 경계로 둔 덕에 자동 테스트는 카메라 없이 돌아감
- **MediaMTX 버전 차이**: 1.21에서 훅 이름이 `runOnReady` → `runOnAvailable`/`runOnUnavailable`로 바뀌어 문서·예제와 달랐다. 실제 컨테이너를 띄워 확인
- **프록시 뒤의 세션 주소**: MediaMTX가 WHIP/WHEP 응답 `Location`을 자기 기준 경로로 줘서 `/media` 접두어가 빠졌다. Caddy·nginx에서 `Location`을 고쳐 송출 종료(`DELETE`)가 닿게 함
- **끊김 감지 시간**: 탭을 닫으면 시청 화면 재생은 바로 멈추지만 서버의 종료 판정은 MediaMTX의 연결 타임아웃(약 30초) 뒤. 시청 화면은 시청 연결이 끊김으로 바뀌면 바로 종료 안내를 보여 주게 했지만, 실제 확인에서는 MediaMTX가 세션을 닫을 때까지 시청 연결도 살아 있어 그동안 마지막 장면에서 멈춘 화면이 보였다
- **병합 충돌**: 02(종료)·03(시간 초과)·04(화면 다듬기)가 같은 서비스·화면 파일을 고쳐 충돌. 두 쪽 동작을 모두 살려 합치고, 병합 뒤 04 테스트가 02의 탭 저장소(송출 키)를 이어받아 깨지는 것을 찾아 테스트 공통 정리에 `sessionStorage.clear()`를 넣음
- **보안 설정은 사람이**: 휴대폰 접속에 필요한 방화벽 허용은 에이전트가 하지 않고 명령만 제시, 사용자가 실행. 규칙은 같은 서브넷으로 제한
- **남은 개선점**: 끊김 감지 30초를 줄이려면 MediaMTX 타임아웃 조정이나 송출 화면의 `beforeunload` 종료 요청을 검토할 수 있음. 같은 LAN 한계는 TURN 서버가 있어야 풀림

## 3단계: 인증·인가, 댓글

### 목표
- 회원가입·로그인·로그아웃. 방송 소유자를 구분하고 등록·수정·삭제·송출 제어 권한을 서버에서 검사한다. 로그인한 회원이 방송별 댓글을 쓰고, 작성자만 수정·삭제한다. 시청·목록은 계속 공개. 1·2단계 기능은 유지한다.

### 주요 결정
- 인증: Spring Security 서버 세션 쿠키(HttpOnly) + CSRF 토큰(쿠키 → 헤더) (ADR-0005). 같은 출처 SPA라 JWT의 장점(무상태)보다 확실한 로그아웃과 토큰 보관 문제 회피를 택함. 대가: 재시작하면 로그아웃, 상태 변경 요청마다 CSRF 헤더
- 송출 키의 역할 축소: MediaMTX 송출 허가에만 쓰고, 종료·수정·삭제는 세션의 소유자로 검사 (ADR-0006). MediaMTX가 브라우저 쿠키를 넘기지 않아서 송출 허가만 키로 남김. 결과: 다른 기기에서도 소유자가 종료 가능, 키가 새도 방송을 끌 수 없음
- 권한 검사 위치: URL 규칙(보안 설정)이 아니라 각 API 옆에 둠. 컨트롤러 파라미터 `LoginMember`(없으면 401) + 서비스의 공통 소유자 검사(403). 응답 순서를 401 → 404 → 403 → 409로 통일. 병행 티켓들이 보안 설정 파일을 함께 고치지 않아도 됨
- 회원: 아이디(로그인용, 비공개) + 비밀번호 + 닉네임(공개, 대소문자 무시 중복 불가). 아이디를 화면에 내보내지 않으려고 둘을 나눔
- 스키마는 Flyway `V3` 하나로: 회원, 두 방송의 소유자 칸(nullable), 댓글. 기존 1·2단계 방송은 "소유자 없음"으로 남겨 아무도 관리할 수 없게 함(데이터 유지 규칙)
- 댓글은 방송 종류 + 식별자로 녹화방송·라이브 방송 모두에 연결. 방송 삭제 → "방송 삭제됨" 이벤트 → 댓글 모듈이 정리. 방송 모듈이 댓글 모듈을 모르게 해서 병행 개발이 가능했음
- 실시간 채팅 대신 3초 폴링(2단계 방식 재사용). 1·2단계에 없던 녹화방송 제목 수정·삭제를 요구사항 때문에 새로 만듦
- 진행은 1·2단계와 같음: 골격 티켓(01)에 공용 기반을 모으고 02~04를 worktree 3개에서 병행, 05에서 병합 후 세 역할로 직접 확인

### 결과·수치
- 테스트: 백엔드 151개(2단계 77 + 74), 프론트 93개(2단계 45 + 48), 모두 green
- TDD 사이클 47개 기록 (`docs/tdd-log.md` #89~#135): 01 10개, 02 10개, 03 14개, 04 11개, 병합 통합 1개, 05 직접 확인에서 찾은 버그 1개
- 세 역할(비로그인·소유자·다른 회원) API 직접 호출 36건이 모두 기대한 401/403/409/2xx (HTTPS, 브라우저처럼 쿠키·CSRF 헤더를 다루는 스크립트)
- 휴대폰 소유자가 송출 → PC의 다른 회원·비로그인은 시청만 가능(버튼 없음, API 403/401) → 소유자가 PC(다른 기기)에서 종료·삭제, 삭제하면 댓글도 함께 사라짐
- 업그레이드 경로: 2단계 데이터가 있는 DB에 `V3`만 적용, 기존 방송 9개가 소유자 없이 남아 재생·조회됨
- 스크린샷: `docs/screenshots/stage-3/` (비로그인 목록·시청, 다른 회원 시청·댓글·종료 화면, 소유자 녹화방송 관리). 휴대폰 화면은 기기 문제로 캡처하지 못함

### 어려웠던 점·배운 점
- **보안 라이브러리 도입의 파급**: Spring Security를 넣자 1·2단계 테스트 70개가 CSRF로 한꺼번에 깨짐. 상태 변경 요청 30곳에 토큰을 붙이고, MediaMTX 내부 훅은 CSRF에서 제외
- **테스트 도구가 만든 가짜 실패**: MockMvc의 `csrf()`가 공유 CSRF 필터의 저장소를 바꿔 두어, 같은 컨텍스트의 실제 서버 테스트에서 쿠키가 사라짐. 필터 체인을 출력해 원인을 찾고 실제 서버 테스트를 별도 클래스로 분리
- **MockMvc와 실제 서버의 차이**: 오류 응답을 쓴 뒤에는 쿠키가 실리지 않아(응답 커밋) 실제 서버에서만 CSRF 쿠키가 빠짐. 응답 전에 토큰을 읽는 필터로 해결. 쿠키 속성(HttpOnly)·CSRF 흐름은 실제 서버에 브라우저처럼 요청하는 테스트로 고정
- **"처음부터 green"인 권한 테스트의 의미 확인**: 01의 기반 덕에 거절 테스트가 처음부터 통과하는 경우가 많았음. 소유자 검사 호출을 잠시 빼서 실패하는 것을 눈으로 본 뒤 되돌림
- **병행 개발의 경계 설계**: 공용 기반(로그인 파라미터, 소유자 검사, 삭제 이벤트, 스키마 전체)을 01에 몰아 둔 덕에 02~04는 각자 파일만 고침. 그래도 같은 화면 두 개와 CSS에서 충돌이 나서 손으로 합쳤고, 병합 후에야 드러나는 연결(삭제 API → 댓글 정리)은 통합 테스트로 확인
- **직접 확인에서 찾은 것**: 제목 수정을 눌러도 입력란에 포커스가 가지 않음(테스트로 고정 후 수정). 화면 버튼은 보조일 뿐이라는 점을 README에 curl 예시로 보여 줌
- **남은 개선점**: 녹화방송 상세와 라이브 시청 화면의 제목 수정 UI가 각자 구현되어 있어 하나로 합칠 수 있음. 세션이 메모리에 있어 재시작 시 로그아웃됨

## 4단계: 도네이션

### 목표
- 로그인한 회원이 방송(방송자)과 금액을 골라 결제 서비스의 테스트 모드로 후원한다. 서버가 결제 승인과 금액·방송자를 확인한 뒤에만 확정하고, 같은 승인 통지가 반복돼도 한 번만 적립한다. 방송별 후원 내역·합계를 보여 준다. 1~3단계 기능은 유지한다.

### 주요 결정
- 결제 서비스: 토스페이먼츠 테스트 모드 + 서버 승인 확인 (ADR-0007). 화면은 결제 화면만 띄우고, 확정은 돌아온 결제 키·주문번호·금액을 서버가 토스 승인 API로 확인해서 정함. 금액과 방송자는 주문을 만들 때 서버가 정해 두고 확인 요청 값과 비교
- **결제창 → 결제위젯으로 변경 (01 진행 중)**: 공식 샘플의 공개 결제창 키가 토스 샌드박스에서 401로 거절됨. 키 종류를 실제로 호출해 보며 원인을 좁힌 뒤, 문서에 공개된 결제위젯 테스트 키로 바꿈. 가입 없이 채점자가 바로 실행 가능
- 중복 확정 방지 (ADR-0008): 코드(확정된 주문은 토스를 다시 부르지 않고 같은 결과) + 저장 구조(주문번호·결제 키 유니크 제약) + 행 잠금(`SELECT … FOR UPDATE`, 동시 요청 한 건만 확정) + 웹훅은 본문 대신 조회 API로 재확인. 웹훅 서명은 계정별 보안 키가 필요해 쓰지 않음
- 모든 승인 통지(확인 요청·웹훅)를 결과와 함께 기록하는 "승인 통지 기록" 테이블. 중복·위조를 DB 조회로 보여 줄 수 있게 함
- 상태 5개: 결제 대기 → 확정 / 실패 / 취소 / 확인 필요. "완료인데 값이 다름"은 자동 확정·실패 대신 확인 필요로 남김(돈은 나갔을 수 있으므로). 웹훅도 같은 규칙(사용자 결정)
- 웹훅 응답은 200이 원칙, 토스 조회가 통신 실패한 경우만 502로 답해 재전송을 받음(사용자 결정)
- 실패 재현용 테스트 헤더(`TossPayments-Test-Code`) 설정은 만들지 않음. 가짜 결제 키로 확인 요청을 보내면 실제 토스가 거절해 같은 서버 경로가 카드 없이 재현됨
- 스키마는 Flyway `V4` 하나(후원, 승인 통지 기록). 후원은 방송을 외래 키로 묶지 않음(두 방송 종류, 방송 삭제 뒤에도 기록 유지)

- 진행: 01(골격)을 함께 하고 02·03을 worktree 2개에서 병행, 03이 끝난 뒤 04, 05에서 병합 후 직접 확인

## 5단계: 로컬 오토스케일

### 목표
- 서버를 컨테이너 이미지로 만들어 로컬 클러스터에서 여러 인스턴스로 실행한다. CPU 사용률로 최소·최대 범위 안에서 자동 스케일 아웃·인 하고, 여러 인스턴스 앞에서 요청을 분산한다. 세션·영상·라이브 상태·댓글·후원은 공용 저장소에 둔다. 부하 스크립트로 인스턴스 수 변화를 보이고, 그동안 상태가 유지됨을 확인한다. 1~4단계 기능과 compose 실행 경로는 유지한다. 클라우드 배포는 하지 않는다.

### 주요 결정
- 오케스트레이터: Docker Desktop 내장 Kubernetes(kind 방식 단일 노드) + 일반 YAML·kustomize (ADR-0011). compose `--scale`은 지표 기반 자동 스케일과 분산 입구를 직접 만들어야 하고, Swarm은 CPU 기반 자동 스케일이 없음. Helm·인그레스 없이 `kubectl apply -k k8s` 하나로 올림
- 세션 공유: Spring Session JDBC로 기존 PostgreSQL에 저장, Flyway `V5` (ADR-0009, ADR-0005의 "세션은 메모리"를 대체). 스티키 세션(인스턴스가 줄면 로그인 소실, 인그레스 필요)·Redis(저장소 하나 더)·JWT(3단계 인증 재설계) 대신. CSRF 토큰은 원래 쿠키라 공유할 것 없음. 부수 효과로 compose에서도 재시작 후 로그인 유지
- 업로드 영상: 모든 백엔드 파드가 같은 PVC를 마운트(코드 변경 없음, ADR-0001 유지). 노드 1대라 `ReadWriteOnce`로 충분하고, 여러 노드면 RWX·오브젝트 스토리지가 필요하다는 한계를 README에 명시
- 라이브 상태 정리: 시작 시 일괄 종료를 없애고 MediaMTX 제어 API와 10초마다 대조, 방송 중인데 송출이 30초(`LIVE_PUBLISH_GRACE`) 넘게 없으면 종료 (ADR-0010). MediaMTX에 닿지 않으면 아무것도 끄지 않음. 제어 API는 인증을 빼고 내부 네트워크에만 둠
- 주기 작업(대기 정리·송출 대조)은 모든 인스턴스에서 돌게 둠. 같은 행을 같은 값으로 바꾸는 작업이라 분산 락(ShedLock) 없이 동시 실행 테스트로 안전함을 고정
- 응답 헤더 `X-Backend-Instance`(값은 `INSTANCE_NAME` 또는 호스트 이름 = 파드 이름)로 어느 인스턴스가 응답했는지 보이게 함. 분산 확인과 상태 유지 확인의 근거
- 자동 스케일: `autoscaling/v2` HPA, CPU 평균 50%(requests 250m 기준), 2~5대, 줄일 때 안정화 60초(기본 300초보다 짧게), 늘릴 때 기본값. 사용자 지정 지표(요청 수)는 Prometheus 어댑터가 필요해 범위 밖
- metrics-server는 공식 릴리스 v0.9.1 매니페스트를 저장소에 그대로 두고 kustomize 패치로 `--kubelet-insecure-tls`만 추가. 클러스터 공용 애드온이라 앱(`k8s/`)과 다른 폴더(`k8s/metrics-server`)에 둬서 앱을 지워도 남게 함
- 데이터 보존: `k8s/storage`(네임스페이스·PVC)와 `k8s/app`을 나눠 `kubectl delete -k k8s/app`은 데이터를 남기고 `kubectl delete -k k8s`만 데이터까지 지움(사용자 결정)
- 진입 포트 `localhost:8000`(compose 3000, 이 PC에서 다른 프로세스가 쓰는 8080 회피), WebRTC 미디어 `localhost:8190`(compose 8189와 분리). Caddy·휴대폰은 Kubernetes 경로에 올리지 않음
- 부하·상태 확인은 k6(`grafana/k6:2.3.0`)를 `docker run`으로. 설치 없이 실행, 세기·시간·주소는 환경변수
- 진행: 01(세션·헤더) → 01에서 발견한 문제로 01b(라이브 대조) 추가 → 02(Kubernetes, 백엔드 2대 고정) → 03(HPA·부하) → 04(문서). 앞 단계와 달리 각 티켓이 앞 티켓에 기대어 순서대로 진행

- **시작 시 정리가 스케일 아웃 때 방송을 끊던 문제**: 2단계에서 넣은 "백엔드가 시작할 때 남은 대기·방송 중을 모두 종료"는 1대일 때는 "재시작 = 모든 연결 끊김"이라 맞았다. 하지만 HPA가 파드를 하나 늘릴 때마다 다른 파드에서 진행 중인 방송이 끝나게 된다. 01에서 세션을 다루다 발견해 02·03 전에 01b를 끼워 넣었고, "인스턴스 C가 떠도 A의 방송이 그대로"를 red로 확인한 뒤 MediaMTX 주기 대조로 바꿈. 한 대 전제로 만든 정리 로직이 여러 대에서는 다른 인스턴스의 상태를 건드린다는 것을 배움
- **MockMvc 세션 테스트 161개 실패**: Spring Session을 넣자 MockMvc의 `MockHttpSession`이 무시되어(세션이 서블릿 컨테이너가 아닌 세션 저장소와 쿠키로 이어짐) 로그인을 전제로 한 기존 테스트 161개가 한꺼번에 깨짐. 호출부를 고치지 않고 테스트 설정(`SessionCookieMockMvcConfiguration`)이 응답의 세션 쿠키를 기억해 다음 요청에 싣도록 해 복구. 세션 ID 교체 테스트는 세션 객체 대신 쿠키 값 비교로 바꿈. 3단계의 Spring Security 도입 때(70개 실패)와 같은 패턴: 저장 방식을 바꾸면 테스트 도구의 가정이 먼저 깨진다
- **metrics-server 인증서 문제**: 공식 매니페스트를 그대로 적용하면 `x509: cannot validate certificate for 172.20.0.2 because it doesn't contain any IP SANs`로 kubelet 지표를 못 받아 metrics-server 파드가 Ready가 되지 않음(이대로면 `kubectl top`·HPA가 CPU 지표를 받지 못함). Docker Desktop(kind 방식) 노드의 kubelet 자체 서명 인증서에 노드 IP가 없어서. 패치 없이 먼저 적용해 원인을 확인한 뒤 `--kubelet-insecure-tls`만 kustomize 패치로 추가하고, 로컬 전용이며 운영에서는 kubelet 서빙 인증서를 발급해야 한다는 이유를 주석에 남김
- **이미지 Pull 정책**: 로컬 빌드 이미지는 보통 `imagePullPolicy: Never`로 쓰지만 Docker Desktop의 kind 방식 클러스터에서는 실패. 노드가 엔진 이미지 저장소를 직접 쓰지 않고 Docker Desktop이 넣은 레지스트리 미러로 받아 오기 때문. `Always`로 두니 미러에서 0.1초대로 받아 오고, 같은 태그로 다시 빌드한 뒤 `rollout restart`만 하면 되어 오히려 편해짐
- **kustomize의 폴더 밖 파일 제한**: MediaMTX 설정 원본(`mediamtx/mediamtx.yml`)을 kustomize가 읽지 못해 `k8s/app/config/`에 사본을 둠. 원본을 고칠 때 함께 고쳐야 한다는 것을 두 파일 주석과 ADR-0011에 기록
- **요청 분산 쏠림 우려**: kube-proxy는 연결 단위로 나누므로 nginx가 백엔드 연결을 재사용하면 한 파드로 몰릴 수 있음. `X-Backend-Instance`로 실제로 세어 보니 nginx upstream keepalive가 없어 요청마다 새 연결이라 고르게 나뉨(조치 없음)
- **JVM 시작 CPU**: 새 파드는 40~55초 동안 준비 전이고 그동안 CPU가 튀지만, readiness 프로브가 통과하기 전 파드는 HPA 계산에서 빠져 더 늘어나지 않았음. 부하가 끝난 뒤 평균 CPU가 잠깐 53%까지 올랐지만 허용 오차(10%) 안이라 스케일하지 않음
- **남은 개선점**: 노드가 여러 대면 업로드를 RWX·오브젝트 스토리지로, 요청마다 세션 쿼리가 DB로 가므로 부하가 더 커지면 DB가 먼저 병목(Redis 검토), 요청 수 기반 스케일(Prometheus 어댑터), Kubernetes 경로의 HTTPS·휴대폰 송출

## 6단계: 설치형 앱 (데스크톱 exe, Android apk)

### 목표
- 브라우저 없이 설치해서 쓰는 앱을 만든다. Windows 데스크톱 앱(exe)과 Android 앱(apk)이 처음 실행할 때 서버 주소를 받아 저장하고, 그 서버의 chzzz 화면을 앱 창에서 연다. 서버의 로컬 인증서는 처음 연결할 때 지문을 확인받아 고정한다. 카메라·마이크는 앱 권한으로 받고, 설치 파일은 GitHub Release `stage-6`으로 배포한다. 웹과 1~5단계 실행 경로는 그대로 둔다.

### 주요 결정
- **서버 화면을 여는 앱** (ADR-0012): 빌드한 프론트를 앱에 넣지 않고 저장한 서버 주소의 화면을 연다. 화면과 API가 같은 출처라 세션 쿠키 `SameSite`·CORS 자격 증명·CSRF·토스 결제 복귀 주소를 다시 설계하지 않아도 되고(ADR-0005·0007 그대로), `frontend/`·`backend/`를 바꾸지 않았다. 대가는 서버 없이 앱만으로 아무것도 못 한다는 것
- **인증서 지문 고정** (ADR-0013): 공인 인증서가 없는 LAN 서버라 앱이 (서버 출처, 서버 인증서 SHA-256) 조합을 사용자 확인 뒤 저장한다. 저장한 출처의 같은 지문만 받아들이고, 지문이 바뀌면 경고와 함께 다시 묻고, 다른 출처는 묻지 않고 거절. 고정할 대상은 선택지(1년 서버 인증서 / 루트 CA 지문 + 체인 검증 / Caddy 기본값 그대로) 중 **Caddyfile에서 루트가 1년짜리 서버 인증서를 직접 발급**(`lifetime 365d`, `sign_with_root`)하게 하고 그 지문을 고정(사용자 선택)
- **주소 열기 규칙**: 앱 안(서버 출처, `https://`의 `tosspayments.com`·`toss.im`과 하위 도메인) / 기본 브라우저(다른 http(s)) / 운영체제(`mailto:`·`tel:`·`intent://`·결제 앱 스킴) / 막음(`file:`·`javascript:`·`data:`·`blob:`·`content:`). 스펙의 "그 밖의 스킴은 운영체제"에서 기기 파일을 열 수 있는 스킴은 막음으로 뺐다. 토스 도메인은 실제 결제위젯 요청을 관찰해 정함
- **같은 규칙 표, 두 구현**: 판단 로직(주소 검증, 연결 확인 해석, 인증서 신뢰, 주소 열기, 권한, 로그인 쿠키)을 Electron·WebView 없는 순수 함수로 두고, 02에서 만든 규칙 표(입력 → 기대 결과)를 Android 티켓이 그대로 JUnit으로 옮김
- **구조**: `apps/shell`(두 앱이 함께 쓰는 시작 화면, 프레임워크 없는 TS + Vite), `apps/desktop`(Electron + TS, 연결 확인은 메인 프로세스 `net.fetch`), `apps/android`(Capacitor + **Kotlin**, 추가 플러그인 없이 앱 안 로컬 플러그인과 WebView 클라이언트 확장). 모두 사용자 선택
- **버전 고정**: Electron 45.2.3, electron-builder 26.18.0, Capacitor 8.6.0(8.6.1·8.6.2는 출시 2주가 안 돼 피함), 빌드 JDK는 Temurin 21. 앱 버전 1.0.0, Android `minSdk 24`(7.0)
- **서명·배포**: exe는 서명 없음(SmartScreen 안내), apk는 저장소 밖 키스토어로 릴리스 서명하고 경로·별칭·비밀번호를 환경변수로만 받음. 비밀번호는 사용자가 터미널에 `Read-Host -AsSecureString`으로 직접 넣어 채팅·저장소·로그에 남기지 않음. 빌드는 이 PC에서 하고 GitHub Actions는 쓰지 않음
- **권한 거절 안내**: Android 앱은 frontend 문구(브라우저 자물쇠 안내)를 고치지 않고 앱이 대화상자로 앱 설정을 안내(사용자 선택)
- **확인 방식**: USB 케이블이 없어 에뮬레이터로 먼저 확인하고, 실제 휴대폰은 apk 파일을 옮겨 설치해 사용자와 함께 확인. 카드 정보는 넣지 않음(4단계 결정 유지)

### 어려웠던 점·배운 점
- **Caddy 12시간 인증서와 지문 고정**: Caddy `tls internal` 기본값은 중간 CA가 12시간짜리 서버 인증서를 발급하고 약 8시간마다 갱신한다. 서버 인증서 지문을 그대로 고정하면 하루에도 여러 번 "지문이 바뀌었습니다"가 뜬다. 루트 CA는 서버가 보내지 않아 루트 지문 고정은 체인 검증을 직접 해야 했다. 루트가 1년짜리 서버 인증서를 직접 발급하도록 Caddyfile만 바꿔 해결. 기존 `caddy-data`의 12시간 인증서는 한 번 갱신될 때 1년 인증서로 바뀌므로 앱이 한 번 더 묻는 것을 README에 남김
- **세션 쿠키 유지**: `JSESSIONID`는 만료 없는 세션 쿠키라 앱을 다시 열면 로그아웃되었다(브라우저 탭과 달리 앱은 매번 프로세스를 새로 시작). 설치본 확인에서 재시작 후 401을 보고, 서버 호스트의 세션 쿠키에 30일 만료를 붙여 다시 저장하도록 데스크톱(#202)과 Android(#210)에 추가. 서버의 세션 유휴 만료(30분)는 그대로라 로그인 규칙은 바뀌지 않음
- **모바일 결제창의 최상위 이동**: PC에서는 결제창이 iframe이라 "최상위 이동·새 창에만 적용"하는 주소 규칙에 걸리지 않았지만, Android에서는 "결제하기"가 결제창 주소로 화면 전체를 옮긴다. 토스 도메인을 앱 안 목록에 넣어 둔 덕에 앱 안에서 열리고, 취소 후 서버 화면으로 같은 로그인 상태로 돌아옴. 결제 도메인 목록을 PC 관찰만으로 정하지 않고 모바일에서 다시 본 것이 중요했다
- **연결 시간 초과 빈 화면**: 서버에 닿지 않으면 WebView가 연결 시간 초과(약 2분 13초)까지 빈 화면을 보였다. 에뮬레이터 NAT가 닫힌 포트의 RST를 넘기지 않아 드러났고, 실기기도 PC가 꺼졌거나 다른 Wi-Fi면 같다. 15초 안에 서버 화면이 열리기 시작하지 않으면 멈추고 연결 실패 화면을 보이게 함. 데스크톱은 서버가 꺼져도 캐시된 화면이 떠서 실패 화면이 안 나오던 문제를 `Cache-Control: no-cache`로 고침
- **에뮬레이터 GPU**: 첫 부팅이 기본 GPU 설정에서 `device offline`에 머물렀다. `-gpu swiftshader_indirect -no-snapshot`으로 띄워 해결
- **그 밖에**: 이 PC의 PowerShell 실행 정책이 `.ps1`을 막아 빌드·서명 명령을 직접 실행(정책은 바꾸지 않음). 카메라가 없는 PC라 데스크톱 송출은 Chromium 가짜 카메라로 확인. USB 케이블이 없어 실제 휴대폰은 apk 파일 전달로 설치. JS `click()`으로 만든 이동 기록은 Chromium이 사용자 동작 없는 기록으로 보고 뒤로 가기에서 건너뛰어, 뒤로 가기는 실제 탭으로 확인
- **남은 개선점**: 코드 서명 인증서(SmartScreen 경고 없애기), 자동 업데이트, 스토어 배포, Android 앱의 서버 주소 변경 메뉴(지금은 연결 실패 화면에서만), 서버 화면 콘솔의 Capacitor `triggerEvent` 오류(동작 영향 없음) 정리
