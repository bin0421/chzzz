## 1단계: 녹화방송 등록·시청

### 목표
- 로그인 없이 녹화방송(업로드 파일 또는 외부 URL)을 등록하고 목록·상세·플레이어로 시청한다. 재시작 후에도 남는다.

### 주요 결정
- 프론트 React + Vite + TS(SPA)와 백엔드 Spring Boot + Kotlin REST API 분리
- PostgreSQL + Flyway: 4단계에 걸친 스키마 변경을 버전으로 관리
- 업로드 파일은 로컬 디스크 + Range 스트리밍 (ADR-0001)
- 외부 URL은 서버에서 접속 확인하지 않음 (ADR-0002)
- 영상 출처를 "종류 + 값"으로 모델링해서 2단계 출처 추가에 대비
- 등록자(소유자)는 3단계로 미룸
- Spring Boot 3.x로 정했으나 Initializr가 3.x를 더 이상 제공하지 않고 3.5 무료 지원도 끝나 4.1.2로 변경
- 테스트 경계는 두 개뿐: 백엔드 HTTP API(Testcontainers 실제 PostgreSQL), 프론트 앱 화면 단위(`fetch`만 스텁)
- 티켓을 수직 슬라이스 6개로 나누고, 골격(01) 이후 02~05를 별도 worktree에서 병행 개발한 뒤 병합

### 결과·수치
- 테스트: 백엔드 26개, 프론트 19개, 모두 green (커버리지는 측정하지 않음)
- TDD 사이클 43개 기록 (`docs/tdd-log.md`): 01 7개, 02 14개, 03 15개, 04 7개. 05(Compose)는 설정 작업이라 TDD 대상 아님
- 직접 확인 절차 7단계를 깨끗한 환경의 `docker compose up --build`에서 모두 통과 (README "직접 확인 절차")
- 스크린샷: `docs/screenshots/stage-1/` (빈 목록, 등록 폼, 외부 URL 재생, 업로드 재생·탐색, 목록, 입력 오류 2종)

### 어려웠던 점·배운 점
- **브라우저 확인에서 찾은 버그**: 등록 응답의 등록일시(나노초)와 DB에 저장된 값(PostgreSQL이 마이크로초로 반올림)이 달랐다. 단위 테스트만으로는 놓쳤을 문제로, 실패하는 테스트를 먼저 쓰고 마이크로초로 잘라 해결 (tdd-log #7)
- **처음부터 green인 테스트의 민감도 확인**: Range 요청(206/416)은 Spring MVC가 이미 처리해서 처음부터 통과했다. 테스트가 의미 있는지 확인하려고 구현을 잠시 바꿔 실패하는 것을 눈으로 확인 (tdd-log #35, #36)
- **MockMvc의 한계**: MockMvc는 multipart 크기 한도를 적용하지 않아서 413 테스트만 실제 포트로 요청
- **설정 형식 차이**: nginx `client_max_body_size`는 Spring의 `500MB` 형식을 받지 않아, 시작 스크립트가 같은 환경변수를 nginx 형식으로 바꾸게 함
- **병행 개발과 병합**: 공유 파일 충돌을 줄이려고 새 테스트는 새 파일에, TDD 기록은 티켓 파일에 따로 남긴 뒤 병합할 때 합쳤다. 결과적으로 02·04·05는 충돌 없이, 03은 main을 먼저 받아 자기 브랜치에서 충돌을 해결한 뒤 병합
- **로컬 포트 충돌**: 8080을 다른 앱이 써서 백엔드 포트(`SERVER_PORT`)와 Vite 프록시 대상(`VITE_API_PROXY_TARGET`), Compose 호스트 포트(`APP_PORT`, 기본 3000)를 모두 환경변수로 뺌
- **남은 개선점**: 등록 폼에는 스타일이 거의 없다(목록·상세만 기본 CSS). 기능 요구사항은 충족하지만 발표 전 다듬을 후보

## 2단계: 라이브 방송 송출

### 목표
- 휴대폰 카메라·마이크로 라이브 방송을 시작·종료하고, 시청자가 방송 목록에서 골라 다른 화면에서 실시간으로 본다. 방송 중·종료를 구분해 표시한다. 로그인 없이, 1단계 기능은 그대로 둔다.

### 주요 결정
- 송출·시청 방식: WebRTC WHIP/WHEP + MediaMTX (ADR-0003). HLS(지연 5~10초)·직접 구현(SFU) 대신 지연이 작고 표준 프로토콜인 쪽. 대가로 같은 LAN 한정(TURN 없음)
- 휴대폰 HTTPS: Caddy 로컬 CA로 LAN IP 인증서 발급 (ADR-0004). 카메라는 보안 컨텍스트에서만 열리기 때문. 대가로 휴대폰에서 인증서 경고를 한 번 넘겨야 함
- 로그인 없는 종료 권한: 방송마다 송출 키를 한 번만 발급하고 해시만 저장. 송출 허가와 종료 API 모두 이 키로 확인
- MediaMTX는 미디어만 다루고 판단은 백엔드가: 송출·시청 허가(HTTP 인증)와 영상 들어옴·끊김 훅을 백엔드 내부 엔드포인트로 받음. `/internal`은 Caddy·nginx에서 바깥에 404
- 상태 모델: 대기 → 방송 중 → 종료. 대기를 둔 이유는 "시작했지만 영상이 아직 안 옴"을 목록에서 숨기고, 60초 안에 오지 않으면 정리하려고. 서비스 재시작 때 남은 대기·방송 중도 종료로 정리
- 목록·시청 화면 갱신은 폴링(목록 5초, 시청 3초). 웹소켓 없이 요구사항(상태 구분 표시)을 충족
- 테스트 경계는 1단계와 같은 두 개 + 이음새 둘: MediaMTX 훅은 테스트가 내부 엔드포인트를 직접 호출, 시간은 바꿔 끼우는 `Clock`, 프론트는 미디어 어댑터(카메라·WebRTC)만 가짜
- 1단계와 같은 진행: 골격 티켓(01) 뒤 02~05를 worktree 4개에서 병행, 06에서 병합 후 휴대폰으로 직접 확인

### 결과·수치
- 테스트: 백엔드 77개(1단계 26 + 51), 프론트 45개(1단계 19 + 26), 모두 green
- TDD 사이클 45개 기록 (`docs/tdd-log.md` #44~#88): 01 10개, 02 14개, 03 10개, 04 11개. 05(Caddy·Compose)는 설정 작업이라 TDD 대상 아님
- 휴대폰 직접 확인(Android Chrome 송출 → PC Chrome 시청): 세로 720×1280 영상 + 소리, 지연은 체감상 거의 없음. 종료 버튼 → PC 시청 화면·목록이 몇 초 안에 종료로 바뀜. 탭 닫기 → MediaMTX가 끊김을 알아챈 약 30초 뒤 자동 종료
- 재시작 후 라이브 방송 기록 유지, 남은 대기는 종료로 정리. 1단계 확인 절차도 같은 실행에서 다시 통과
- 스크린샷: `docs/screenshots/stage-2/` (PC 목록 방송 중, 시청 재생, 시청 종료, 목록 종료). 휴대폰 화면은 기기 문제로 캡처하지 못함

### 어려웠던 점·배운 점
- **개발 PC에 카메라가 없음**: 01 골격 확인은 `getUserMedia`를 캔버스+사인파 합성 스트림으로 바꾸고, 서버 경로는 ffmpeg WHIP 송출로 확인. 실제 카메라는 마지막에 휴대폰으로 확인. 미디어 어댑터를 경계로 둔 덕에 자동 테스트는 카메라 없이 돌아감
- **MediaMTX 버전 차이**: 1.21에서 훅 이름이 `runOnReady` → `runOnAvailable`/`runOnUnavailable`로 바뀌어 문서·예제와 달랐다. 실제 컨테이너를 띄워 확인
- **프록시 뒤의 세션 주소**: MediaMTX가 WHIP/WHEP 응답 `Location`을 자기 기준 경로로 줘서 `/media` 접두어가 빠졌다. Caddy·nginx에서 `Location`을 고쳐 송출 종료(`DELETE`)가 닿게 함
- **끊김 감지 시간**: 탭을 닫으면 시청 화면 재생은 바로 멈추지만 서버의 종료 판정은 MediaMTX의 연결 타임아웃(약 30초) 뒤. 시청 화면은 시청 연결이 끊김으로 바뀌면 바로 종료 안내를 보여 주게 했지만, 실제 확인에서는 MediaMTX가 세션을 닫을 때까지 시청 연결도 살아 있어 그동안 마지막 장면에서 멈춘 화면이 보였다
- **병합 충돌**: 02(종료)·03(시간 초과)·04(화면 다듬기)가 같은 서비스·화면 파일을 고쳐 충돌. 두 쪽 동작을 모두 살려 합치고, 병합 뒤 04 테스트가 02의 탭 저장소(송출 키)를 이어받아 깨지는 것을 찾아 테스트 공통 정리에 `sessionStorage.clear()`를 넣음
- **보안 설정은 사람이**: 휴대폰 접속에 필요한 방화벽 허용은 에이전트가 하지 않고 명령만 제시, 사용자가 실행. 규칙은 같은 서브넷으로 제한
- **남은 개선점**: 끊김 감지 30초를 줄이려면 MediaMTX 타임아웃 조정이나 송출 화면의 `beforeunload` 종료 요청을 검토할 수 있음. 같은 LAN 한계는 TURN 서버가 있어야 풀림

## 3단계: 인증·인가, 댓글

### 목표
- 회원가입·로그인·로그아웃. 방송 소유자를 구분하고 등록·수정·삭제·송출 제어 권한을 서버에서 검사한다. 로그인한 회원이 방송별 댓글을 쓰고, 작성자만 수정·삭제한다. 시청·목록은 계속 공개. 1·2단계 기능은 유지한다.

### 주요 결정
- 인증: Spring Security 서버 세션 쿠키(HttpOnly) + CSRF 토큰(쿠키 → 헤더) (ADR-0005). 같은 출처 SPA라 JWT의 장점(무상태)보다 확실한 로그아웃과 토큰 보관 문제 회피를 택함. 대가: 재시작하면 로그아웃, 상태 변경 요청마다 CSRF 헤더
- 송출 키의 역할 축소: MediaMTX 송출 허가에만 쓰고, 종료·수정·삭제는 세션의 소유자로 검사 (ADR-0006). MediaMTX가 브라우저 쿠키를 넘기지 않아서 송출 허가만 키로 남김. 결과: 다른 기기에서도 소유자가 종료 가능, 키가 새도 방송을 끌 수 없음
- 권한 검사 위치: URL 규칙(보안 설정)이 아니라 각 API 옆에 둠. 컨트롤러 파라미터 `LoginMember`(없으면 401) + 서비스의 공통 소유자 검사(403). 응답 순서를 401 → 404 → 403 → 409로 통일. 병행 티켓들이 보안 설정 파일을 함께 고치지 않아도 됨
- 회원: 아이디(로그인용, 비공개) + 비밀번호 + 닉네임(공개, 대소문자 무시 중복 불가). 아이디를 화면에 내보내지 않으려고 둘을 나눔
- 스키마는 Flyway `V3` 하나로: 회원, 두 방송의 소유자 칸(nullable), 댓글. 기존 1·2단계 방송은 "소유자 없음"으로 남겨 아무도 관리할 수 없게 함(데이터 유지 규칙)
- 댓글은 방송 종류 + 식별자로 녹화방송·라이브 방송 모두에 연결. 방송 삭제 → "방송 삭제됨" 이벤트 → 댓글 모듈이 정리. 방송 모듈이 댓글 모듈을 모르게 해서 병행 개발이 가능했음
- 실시간 채팅 대신 3초 폴링(2단계 방식 재사용). 1·2단계에 없던 녹화방송 제목 수정·삭제를 요구사항 때문에 새로 만듦
- 진행은 1·2단계와 같음: 골격 티켓(01)에 공용 기반을 모으고 02~04를 worktree 3개에서 병행, 05에서 병합 후 세 역할로 직접 확인

### 결과·수치
- 테스트: 백엔드 151개(2단계 77 + 74), 프론트 93개(2단계 45 + 48), 모두 green
- TDD 사이클 47개 기록 (`docs/tdd-log.md` #89~#135): 01 10개, 02 10개, 03 14개, 04 11개, 병합 통합 1개, 05 직접 확인에서 찾은 버그 1개
- 세 역할(비로그인·소유자·다른 회원) API 직접 호출 36건이 모두 기대한 401/403/409/2xx (HTTPS, 브라우저처럼 쿠키·CSRF 헤더를 다루는 스크립트)
- 휴대폰 소유자가 송출 → PC의 다른 회원·비로그인은 시청만 가능(버튼 없음, API 403/401) → 소유자가 PC(다른 기기)에서 종료·삭제, 삭제하면 댓글도 함께 사라짐
- 업그레이드 경로: 2단계 데이터가 있는 DB에 `V3`만 적용, 기존 방송 9개가 소유자 없이 남아 재생·조회됨
- 스크린샷: `docs/screenshots/stage-3/` (비로그인 목록·시청, 다른 회원 시청·댓글·종료 화면, 소유자 녹화방송 관리). 휴대폰 화면은 기기 문제로 캡처하지 못함

### 어려웠던 점·배운 점
- **보안 라이브러리 도입의 파급**: Spring Security를 넣자 1·2단계 테스트 70개가 CSRF로 한꺼번에 깨짐. 상태 변경 요청 30곳에 토큰을 붙이고, MediaMTX 내부 훅은 CSRF에서 제외
- **테스트 도구가 만든 가짜 실패**: MockMvc의 `csrf()`가 공유 CSRF 필터의 저장소를 바꿔 두어, 같은 컨텍스트의 실제 서버 테스트에서 쿠키가 사라짐. 필터 체인을 출력해 원인을 찾고 실제 서버 테스트를 별도 클래스로 분리
- **MockMvc와 실제 서버의 차이**: 오류 응답을 쓴 뒤에는 쿠키가 실리지 않아(응답 커밋) 실제 서버에서만 CSRF 쿠키가 빠짐. 응답 전에 토큰을 읽는 필터로 해결. 쿠키 속성(HttpOnly)·CSRF 흐름은 실제 서버에 브라우저처럼 요청하는 테스트로 고정
- **"처음부터 green"인 권한 테스트의 의미 확인**: 01의 기반 덕에 거절 테스트가 처음부터 통과하는 경우가 많았음. 소유자 검사 호출을 잠시 빼서 실패하는 것을 눈으로 본 뒤 되돌림
- **병행 개발의 경계 설계**: 공용 기반(로그인 파라미터, 소유자 검사, 삭제 이벤트, 스키마 전체)을 01에 몰아 둔 덕에 02~04는 각자 파일만 고침. 그래도 같은 화면 두 개와 CSS에서 충돌이 나서 손으로 합쳤고, 병합 후에야 드러나는 연결(삭제 API → 댓글 정리)은 통합 테스트로 확인
- **직접 확인에서 찾은 것**: 제목 수정을 눌러도 입력란에 포커스가 가지 않음(테스트로 고정 후 수정). 화면 버튼은 보조일 뿐이라는 점을 README에 curl 예시로 보여 줌
- **남은 개선점**: 녹화방송 상세와 라이브 시청 화면의 제목 수정 UI가 각자 구현되어 있어 하나로 합칠 수 있음. 세션이 메모리에 있어 재시작 시 로그아웃됨
